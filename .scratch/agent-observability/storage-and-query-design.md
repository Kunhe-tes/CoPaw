## 1. 责任边界

| 项目负责 | 用户负责 |
|---|---|
| 独立元数据 JSON、schema 和枚举、字段限额及样例 | 从 stdout 采集日志 |
| 专用日志队列、输出和失败降级 | 采集代理、网络传输、缓冲/重放与调度 |
| 独立MySQL逻辑模型、DDL、访问索引与数据归并设计 | 按已交付契约将日志写入原始事件存储 |
| 数据库内去重规则、事件到查询视图的确定性归并设计与所需应用代码 | 生产入库账号、采集入库任务运维 |
| SWE 独立查询/权限/正文解析/API、Console 新页面 | 生产环境资源和连接信息的配置 |
| 使用契约样例灌入测试库并验证查询/归并/页面 | 生产采集与人工入库的正确性和时延 |

“人工处理入库”指用户接管采集与写入操作，不意味着本项目可以省略 schema、事件幂等键、去重/乱序约定、查询模型与失败状态。任何依赖外部加工的规则必须在交付契约中明确，不能只留一句“日志平台处理”。

## 2. 逻辑数据分层

1. **原始元数据事件**：白名单元数据，event_id 标识一条事实，重复投递内容不变；同 event_id 不同内容视为冲突，不按到达顺序静默覆盖。数据库生成独立入库时间供排错，不替代 occurred_at。
2. **Run 查询视图**：新 obs_run_id + 业务问题定位，状态以业务受理/终态事实为准；日志提供阶段、计数及观测质量。没有日志的已受理问题仍在统计总体中，显示详情未采集。
3. **Attempt/Span 查询视图**：按新 ID 归并生命周期；每个结束事件携带足以展示该操作的终态元数据，避免结束先到时必须等起始事件才能显示。缺起始事件仍标 partial，不伪造完整。
4. **关系和资产**：业务父子/重执行前驱/恢复关系明确类型；资产只保留执行时实际身份/可信版本；不得查询旧追踪补全。

采用独立MySQL原始事件表和Run/Attempt/Span查询表，避免每次列表查询扫描全部原始事件。导入方式必须支持重复/乱序；如果只写原始事件，归并能力由本项目提供，不能暗含用户实现第二个处理系统。

## 3. 必须支持的查询模式

| 查询 | 必须先应用的范围 | 排序与索引方向 |
|---|---|---|
| Run 列表 | service_unit + 授权 source/tenant/agent 集合 | 受理时间 + 稳定 Run/业务问题键，游标分页 |
| Run / Span 详情 | 同上，先验证 Run 业务关联 | obs_run_id + obs_span_id；起止事件可乱序，不能只按日志到达排序建树 |
| 业务问题查 Run | scope + chat/question identity | 精确业务键，终态后重执行可以有多条 Run |
| 模型/工具/类型/状态筛选 | 同上 + 有界时间窗 | 类型化标量字段，不对任意 attributes 做动态无界索引 |
| 错误定位 | 同上 + 有界时间窗 | error.type/phase/终态，错误自由文本不入库 |
| 性能聚合 | 同上 + 明确统计总体和窗口 | 时长、已知 Usage、完整/部分覆盖分别处理 |
| 正文展示 | 业务授权再次检查 | 用业务 locator 从 MySQL/NAS 查询，不从元数据存储取正文 |

不以用户可控字符串拼索引名/SQL；不提供无约束全文 DSL/SQL 透传。API 明确分页上限、时间窗与详情节点上限；超限继续分页或显示截断，不默默只取前 N 条当完整树。

## 4. 时序、身份和缺失

- event_id 不等于 Span/Run ID；一个 Span 有多种事件。事件身份跨重传保持，进程重新产生的新事实用新 event_id。
- 顺序由业务 Attempt/Span 身份、事件类型、同一生命周期内显式 revision/sequence 决定；不以不同机器墙钟或入库顺序最后写覆盖。
- Run 终态不可重开；新问题或终态后重执行新 Run，记录 predecessor。重连只读。
- 父子节点缺失则展示 orphan 标记，不能按名字/时间猜 Parent；父 Run 终态不覆盖后台 SubAgent 的独立终态。
- 一个结束事件能显示操作终态，不证明该 Run 其它操作全量到达。采集覆盖、日志可用性、Usage 已知、正文可读性是不同维度。
- 本项目只验证存储已接收的事件和归并正确性，不承诺用户日志采集/入库的端到端完整性或时延。

## 5. 数据保留与正文可见性

原始事件/查询视图仅保留元数据。本期不设计或实现自动清理、TTL、按龄归档或分区淘汰；元数据持续保存在数据库。不把暂不清理解释为数据库永不增长的容量承诺。元数据存留不延长正文访问。NAS 正文原有删除/授权/归档规则始终有效。若统计使用实时业务元数据，业务删除可能改变可查询统计总体，必须标“当前可查询业务范围”；如需删除后不可变历史审计分母，需要另行确认持久化摘要与删除治理，不暗自增加审计副本。

## 6. 验收交付物

- 独立 schema、字段字典、样例 JSONL；正常、取消、拒绝、恢复、SubAgent、缺 Usage、缺事件样例。
- 独立MySQL存储定义与索引、幂等/冲突/乱序规范、不自动清理的范围说明；与原业务及旧可观测表/索引无写耦合。
- 独立查询与归并实现、版本不兼容/非法事件处理约定，不因一条坏数据让整页失败。
- 覆盖样例导入后的列表、树/瀑布、Inspector、统计及 NAS 授权正文读取。
- 不交付采集代理、部署日志路由、生产数据搬运或采集链验收。

## 7. 已确认的存储技术

首期采用独立 MySQL 元数据存储，单独连接配置和表命名空间（如 swe_agentobs_*），不读写旧可观测表，也不修改会话表。已有通用 DatabaseConnection/参数化查询能力可用于新模块，不构成旧可观测依赖。当前会话 DDL 的 MySQL 8.0.21+ 是该子系统目标，审计环境 8.0.46 不是生产版本保证；新 DDL 仍要明确目标并验收兼容。

以 swe_agentobs_inbox 为用户入库落点，保留 event_id 幂等键、业务 scope、run/attempt/span 关联、事件类型/生命周期序号、发生时间、入库序号、类型化筛选列及受限 metadata_text。原始表不包含正文，扩展文本由应用 schema 校验；不依赖任意 JSON 字段动态索引。具体主键长度、字符集/大小写语义及唯一键宽度须在 DDL 设计中核算。

Run/Span 派生表和归并进度由 SWE 独立模块维护，不要求人工入库任务同时更新多张查询表。它们可从原始事件重建；新幂等事件的接收不能因派生失败丢失。并发、多Pod处理权、原始事件晚提交导致游标漏读的处理、冲突事件隔离必须一并设计，不能只用“MAX(id)之后扫描”宣称安全。归并器无论部署为现有SWE生命周期内任务还是按需处理，都不另建必须部署的新服务。

复合索引从scope和高频等值条件开始，再安排时间/稳定排序键，按实际查询验证，不给每个属性建索引。MySQL 官方说明复合索引依赖最左前缀，且不必要索引会增加成本：
- https://dev.mysql.com/doc/refman/8.0/en/multiple-column-indexes.html
- https://dev.mysql.com/doc/refman/8.0/en/optimization-indexes.html

不引入ES/OpenSearch，不双写其它检索存储。MySQL容量必须以实际数据和查询验收；当前选择不代表已完成性能验证。

## 8. MySQL 表与索引设计草案

以下为逻辑DDL准备，不执行建表、不修改生产数据。表统一采用独立命名空间 swe_agentobs_*，独立数据库连接；scope值与ID长度按业务允许值和InnoDB索引宽度逐项核算，不能把任意长字符串直接拼成唯一键。所有时间统一UTC，耗时用明确单位的整数。

| 表 | 责任 | 主键/核心访问索引方向 |
|---|---|---|
| swe_agentobs_inbox | 用户直接插入的单行元数据JSON及默认处理状态；不要求采集端拼Run/Span查询表 | 数据库ingest_id主键；pending处理索引(state,ingest_id)；received_at仅用于入库诊断 |
| swe_agentobs_events | 校验后的规范事件、幂等event_id和允许的扩展字段 | event_id唯一；(run_id,occurred_at,event_id)；(service_unit,source,occurred_at,event_id) |
| swe_agentobs_runs | 新Run查询视图、业务锚点、终态/等待状态、开关快照、质量信息 | run_id主键；scope+started_at+run_id；业务问题关联键；predecessor_run_id |
| swe_agentobs_attempts | Agent层连续执行片段，非模型重试 | attempt_id主键；(run_id,attempt_index)；唯一序号的生成/跨进程规则须明确 |
| swe_agentobs_spans | 实际操作起止、父节点、类型、模型/工具、Usage和受限错误分类 | span_id主键；(run_id,start_time,span_id)；(run_id,parent_span_id,start_time,span_id)；按真实热点另加scope/type/model索引 |

不预先增加关系表、资产表或全局指标仓：P0的有界关系/资产引用先放经schema校验的元数据文本，Run/Span核心筛选使用标量列。若反向查询确需索引，再据P1范围扩展。inbox是待处理的日志元数据，不是正文存储。表不启用TTL或自动归档。

### 8.1 人工入库的最小落点

用户按契约把完整单行JSON写到inbox.payload_text，其余ingest_id、received_at、processing_state等由数据库默认值生成。该设计不要求人工采集任务解包所有字段或维护派生表。账号仅有inbox必要INSERT权限；查询/归并服务使用独立最小权限账号，不能从客户端透传SQL。给出固定INSERT样例与schema验证样例，但不编写采集代理。

同一事件重复导入可以有多个inbox行，event_id在规范事件层去重。这样不同采集工具无需实现复杂upsert；同ID不同合法载荷冲突由本项目归并器隔离，不以INSERT IGNORE悄悄掩盖。schema不兼容/超限/正文混入/非法scope的inbox行不得进入规范查询表。payload超限限制同时在契约和入库列/应用校验中明确。无效载荷可能含违规正文，投影校验拒绝时立即清空该行payload，仅保留inbox_id、状态和安全原因枚举，不回显或重打原文。此为入库校验处置，不是按龄清理；合法元数据不删。

### 8.2 原子归并与乱序

采用现有SWE应用生命周期内的独立投影任务，不另起必须部署的服务。多Pod从inbox领取pending行；一批记录在有界事务中锁定、校验、幂等写规范事件及Run/Attempt/Span、标记processed。数据错误隔离该行，不拖垮整批；数据库故障回滚并保留pending，任务异常不影响Agent业务执行。具体锁/跳锁语法以新DDL最低MySQL版本验证后确定。

不使用MAX(ingest_id)全局高水位来排除历史行：较小ingest_id可能较晚提交。处理条件是数据库中已提交的pending状态，因此晚提交小ID仍可被领取。事件归并与processed在同事务，进程崩溃时全部回滚可重试。重复event_id的规范化内容相同则不再叠加计数；不同则标conflict，保持原已接收事实。比较采用确定性白名单规范化载荷，不复用会话业务的版本/指纹体系。

start/end可乱序，终态事件携带完整且有界的该操作结束摘要。end先到时可构造partial操作视图，start后到补齐开始证据而非清除已知终态；不按“最后入库”改状态。冲突终态需标记并使用业务Run结算规则，不将日志墙钟先后当权威。计数与Usage由唯一操作事实派生，不对每次重传累计加值。

### 8.3 查询与无日志业务事实

列表支持两种明确视图：业务总体（当前可查询的受理问题/终态）和已采集Run。无日志问题返回业务定位及observability=not_collected，不伪造obs_run_id；只要后续日志精确匹配才显示新Run身份。审批业务轮次与Run不是一对一，是否将多个业务轮次归为一个Run取决于独立审批结算契约，不能直接COUNT业务Turn作为Run数。

运行总览的成功率等业务统计、日志覆盖率和观测到的模型/工具性能分别返回population_source、window、count/coverage、generated_at。不支持跨库跨NAS数据库事务；查询受理/终态与日志投影出现短时差异时显示各自截至信息，不宣称全局原子快照。

日志导入延迟时，界面显示“尚未采集/尚未入库/投影待处理或缺失”的可证明状态；无法区分时为unknown，不用估计制造精确采集延迟。最后入库/投影时间不证明所有更早事件都已到达。查询仅依据数据库已入库事实刷新，不依赖实时日志流或现有SSE通道。
