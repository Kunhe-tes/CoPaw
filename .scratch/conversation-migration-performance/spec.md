# 会话迁移有界批处理与 IO 优化

Status: ready-for-agent

类型：性能优化规格。发布位置：本地 Markdown issue tracker。
日期：2026-11-16。代码分析基线：`2af427705`。
本规格遵循 ADR 0046 与 ADR 0049；后者定义新作业以 source 为独立失败、重试和发布单位。

## Problem Statement

运维人员在只有几百用户、每用户一个 workspace 的测试环境中观察到迁移运行超过 40 分钟后报错。该次环境尚未部署增强的锁诊断，尚无足够阶段耗时和数据量证据确认现场总耗时或锁错误的完整根因。

已有优化减少了重复结构查询和同一 SQL owner 内的全量 journal 恢复，但离线迁移仍存在与消息数线性增长的单条 SQL 和事务、重复关联锁及 bundle 索引读取。用户需要在保留数据完整性、source 失败隔离和断点恢复的前提下缩短迁移时间，而不是单纯增大容量或 worker 参数。

计数复现已确认：128 条新消息的票据分配产生 128 次 SELECT、128 次 INSERT、128 次 UPDATE 和 128 次事务；消息安装另产生 128 次 INSERT。已提交批次核对 128 条记录另需 128 次 SELECT，该路径不能误算为每个新批次的必经成本。现有迁移批次大小控制 publication 组织，不等于真正的 SQL 批量插入。

## Solution

保留主要操作 prepare 与 migrate（显式 apply），让现有离线迁移透明使用有界的业务记录批量插入、票据批量分配、集合加锁与核对，以及同文件多块读取。对作业级重复注册、归属扫描和镜像序列化按实测进一步优化。

优化始终保留同一 source 完整导入、全量语义验证、最后源复查及独立发布的依赖关系。正常 source 继续迁移，坏 source 记录并跳过；数据库身份或命名锁丢失、共享 IO 故障及提交结果不确定仍全局停止。通过阶段与资源指标证明收益，不承诺未经环境对比验证的总耗时倍数。

## User Stories

1. As a 迁移运维人员, I want 继续使用 prepare 和 migrate 两个主要操作, so that 性能优化不会增加人工迁移阶段。
2. As a 迁移运维人员, I want 消息元数据按有界 SQL 块插入, so that 大量消息不会产生逐条 INSERT 往返。
3. As a 迁移运维人员, I want 消息票据按批次分配, so that 不必为每条消息支付独立事务开销。
4. As a 数据维护人员, I want 从数据库真实结果获得票据 ID, so that 自增间隙和并发在线写入不会造成错误映射。
5. As a 迁移运维人员, I want 已有和缺失票据可以混合恢复, so that 中断后使用原作业安全续跑。
6. As a 迁移运维人员, I want 批量操作同时受行数、字节与 packet 限制, so that 大字段不会使数据库请求或内存失控。
7. As a 数据维护人员, I want 每行关联及归属检查继续执行, so that 批量化不会引入跨 source 数据污染。
8. As a 迁移运维人员, I want 同一 publication 内的写入保持原子性, so that 一条坏记录不会留下半个已发布批次。
9. As a 迁移运维人员, I want 消息批次只锁定实际关联的 Session、Chat 和 Turn, so that 长会话不会放大每批锁查询。
10. As a 数据维护人员, I want 集合锁保留确定的锁顺序和缺失行检查, so that 优化不会改变冲突处理和完整性保护。
11. As a 迁移运维人员, I want 已提交批次按集合查询后逐行比较, so that 续跑更快且仍是全量核对。
12. As a 迁移运维人员, I want 同一 bundle 的多块正文复用安全打开和索引解析, so that NAS 小读取与元数据访问减少。
13. As a 安全维护人员, I want 多块读取继续拒绝软链接、越界、特殊文件、截断和异常替换, so that IO 优化保持输入安全边界。
14. As a 迁移运维人员, I want 失败 source 只记录并跳过, so that 同一租户的正常 source 仍可继续和独立上线。
15. As a 已上线 source 的用户, I want 后续迁移不重读旧输入或覆盖新数据, so that 补迁其他 source 不影响我的正常会话。
16. As a 迁移运维人员, I want 共享基础设施故障明确停止并保留断点, so that 未知提交不会被误判为可忽略的账号错误。
17. As a 迁移运维人员, I want 所有并发任务共享 worker、IO、内存和临时盘预算, so that 批量化不会突破资源门禁。
18. As a 数据维护人员, I want 老 manifest、票据与 publication 身份保持兼容, so that 已准备和部分完成的作业无需重建。
19. As a 迁移运维人员, I want 自动重审复用一次有界归属分析, so that 多个失败 source 不重复扫描整个作业。
20. As a 迁移运维人员, I want 看到 SQL、事务、NAS 打开和阶段耗时统计, so that 可以判断瓶颈并对比优化前后结果。
21. As a 数据维护人员, I want 正文、凭据和 SQL 参数不进入性能日志, so that 诊断信息可安全收集。
22. As a 维护人员, I want 每一步优化独立测试和回退, so that 出现回归时可以定位并撤销最小改动。

## Implementation Decisions

- 继续采用单 SQL owner；worker 只处理获准的解析和正文 IO，不共享活跃数据库 session，也不跨 source 合并事务。
- 第一增量为离线业务记录批量插入与已提交记录批量核对；第二增量为票据分配与关联锁优化；第三增量为 bundle 多块读取；第四增量为有测量依据的作业重复工作消除。每个增量可独立交付和回退。
- 优先对 Message 新增记录使用现有 prepared 多行插入能力。按相同表、相同字段集合和既定依赖顺序组织连续记录；不任意重排 Session、Chat、Turn、Message 和更新记录。其他表仅在证明依赖与顺序等价后扩展。
- 表与字段来自可信白名单，值全部参数化；不得使用忽略错误、无条件覆盖或静默降级掩盖冲突。
- 复用既有行数、字节和服务器 packet 限制，不将 publication 批次大小等同于 SQL 请求大小。超限分块；单行超过服务器安全预算必须明确失败。首轮不增加不必要的 CLI 调参项。
- 业务批量写入保持当前 publication 的事务边界。数据错误回滚当前事务，并按已有领域错误分类隔离 source；未知数据库异常不得转换为 source 输入失败。
- 已提交记录按表及有界 ID 集合读取，再执行原有逐条不可变字段比较；显式检查缺失记录、重复输入身份与不一致，不能使用抽样代替。
- journal 新增有界 allocate_many 能力，单条 allocate 保持兼容。一次事务内检查已有票据、批量插入缺失票据、按完整唯一键重读真实身份、批量回填 target_id 并核对映射；提交成功后才更新内存镜像。
- 不假设自增连续，不依据首个 last-insert-ID 推算后续身份；不更改稳定源 key、operation key、票据 kind 或 target_id=id 的契约。新旧票据混合、重试与未知提交仍有明确语义。
- 批量票据先接入 Message，再接入 Turn 与 Session/Chat；Publication 携带 scope 和定位约束，最后在同等核对充分时接入。不预分配整个大 source。
- 消息批次只声明实际引用的 Chat 与 Turn，并保留必要 Session 关联。集合加锁使用固定表顺序、确定 ID 组织与有界查询；缺失行及每行关系继续校验。实际锁顺序与冲突行为须在 MySQL 验证，不能仅凭 ORDER BY 推断。
- bundle 多块读取使用受限生命周期的文件描述符和一次索引解析；逐 extent 校验边界、长度与 publication 身份，并在同一次读取中执行既有安全契约要求的复查。禁止长期或跨命令缓存正文证据。
- 优先把多块读取接入运行时正文预取、同 publication 的消息读取、import plan 与关联恢复证据。保留 fsync、最终源复查和全部语义验证。
- 作业重复工作优化包括：避免无差异的重复注册、批量读取选择与重审所需状态、同次重审建立有界磁盘票据归属索引、为 source 视图建立只读分组索引。证据修订、SQL 写入或映射替换后，相关复用结果必须更新或失效。
- 仅在绑定数据未变化的明确生命周期内复用序列化结果。manifest 镜像持久化频率先量化再调整；SQL 权威、崩溃恢复、审计持久性和已有文件格式不能削弱。
- 不计划更改数据库 schema、公开 CLI 契约、bundle 格式或运行时准入协议。若实测证明必须改变，另立设计决策，不在性能修复中隐式引入。
- 性能统计区分逻辑数据库门面调用与真实 SQL 分块、事务开始/提交/回滚，以及并发累计 IO 时间和墙钟时间。补充阶段耗时、记录数、bundle 打开和索引解析次数；指标不得包含会话正文、凭据、敏感路径或 SQL 参数。

## Testing Decisions

- 主测试边界：复用现有 prepare → migrate CLI/编排集成入口，以隔离 MySQL 与本地目录执行、重跑和注入故障。主要验证可观察结果、SQL 持久状态、source 准入与恢复行为；必要底层单测补充 packet 分块、SQL owner 和安全文件读取。
- 优先复用现有 CLI、source 隔离、journal、offline commit/verify、数据库 prepared insert 与 bundle 安全测试；避免为每层引入全新测试入口。
- 正确性测试不依赖私有 helper 调用顺序；专门的性能回归可统计实际 SQL/事务和 IO 次数，以明确约束逐条往返消除，并与数据语义断言同时运行。
- 覆盖空、单条、满块、跨块、不同字段集合、Unicode/二进制/空值、大字段、packet 边界和单行超限。输入数据必须真实通过现有类型及关联校验。
- 覆盖已有、缺失、混合及冲突票据，自增间隙与其他合法身份分配，重复请求、事务回滚、提交响应丢失及进程重启；不通过连续 ID 假设让测试通过。
- 覆盖同租户一个坏 source 和一个正常 source，正常者完成并可准入，失败者仍关闭并记录安全原因；已发布 source 的新增数据在补迁和重试后保持不变。
- 覆盖源文件新增、删除、修改、替换，软链接、越界、特殊文件、正文截断及异常文件替换；优化后仍必须发现。
- 覆盖命名锁丢失、连接身份变化、数据库故障、共享 IO 错误、临时盘耗尽、取消和 UnknownCommit；全局停止、IO 排空与恢复证据必须保持。
- 关联锁优化使用真实 MySQL 验证执行计划、行锁与冲突行为；本地假数据库计数不代替该验收。
- 对同一冻结数据、同一 worker/IO/预算与相同数据库环境做前后对照：小 source 多账号、单大 source、多 Session/Turn/Message、分享/归档/事件/checkpoint 和混合失败场景。用户不要求恢复万级基线。
- 性能验收要求新增票据事务和业务 INSERT 从逐消息增长转为按受限块增长，已提交核对从逐行查询转为按表分块，同一多块读取内索引只解析一次。具体墙钟收益据实报告，不设未经测量的倍数承诺。
- 每步验证内存、临时盘和 SQL packet 预算，运行相关回归、会话存储与 CLI 全套测试及项目提交检查。明确区分本地目录、隔离 MySQL、真实 NAS 和现场验收范围。

## Out of Scope

- 新的迁移人工阶段、全量重建作业、删除控制票据或自动重绑已有业务数据。
- 多 SQL owner、多迁移 CLI 并行写同库、跨 source 大事务、跳过锁保护或自动重拿丢失的命名锁。
- 删除校验、抽样取代全量语义检查、关闭 fsync、扫描附件/代码/技能目录或放宽会话输入安全边界。
- 修改在线会话 CRUD、发布准入协议、分享权限或原地迁移的停写和输入冻结要求。
- 首轮合并 Turn recovery bundle 或改变 reader 格式；每 Turn 多 publication 的优化另行设计。
- 生产部署、真实 NAS 放行、万级基线、固定旧镜像回滚验收或未经同环境测量的总耗时保证。

## Further Notes

- 现有 22 次逐表结构查询降为 3 次批量读取、同一 SQL owner 内复用 journal 恢复的优化已在基线中，本规格不重复实现。
- 锁丢失诊断与性能优化是两个问题；减少运行时间不等于修复代理会话切换、实例切换或数据库连接重置。
- 调大 workers 无法消除单 SQL owner 的逐行往返。先优化 SQL 形态与锁集合，再根据观测判断是否需要其他并发架构。

- 本规格是性能优化实施的唯一权威副本，原设计草稿仅保留跳转入口。
