# Independent Agent Observability Uses Metadata Logs and NAS Content

On 2026-11-15 the user explicitly chose a new, independent Agent observability scheme: new instrumentation emits metadata logs, and authorized content views resolve existing conversation bodies from NAS. It does not integrate with, modify, wrap, migrate, consume, or depend on the existing swe.tracing or AgentTraceSDK pipelines, their instrumentation, configuration, identifiers, exports, storage, or query APIs. Existing tracing may continue to operate independently; its private SDK availability is not a release gate for this feature. Sharing the same business execution code is necessary to observe actual operations, but the new hooks and context must not alter old instrumentation or make business execution depend on observability success.

This deliberately accepts a separate instrumentation and event contract instead of reusing the SDK, so that the new feature can evolve and fail independently. Logs contain identity, lifecycle, timing, usage when actually known, and controlled references, never conversation/model/tool bodies or free-form exception payloads. NAS remains the content source; logging does not create a second body copy. Business identity and authorized conversation-domain reads may locate that content without using old tracing logic. UI location, log collection/indexing/query backend, identifiers, retention, and delivery budgets still require design decisions; this ADR does not choose them.

The initial audience is authorized Source operators and system administrators. P0 covers main conversation execution, Expert Main Execution, and basic background SubAgent association and terminal state; Cron and independent Workflow are P1. An Observability Run represents one user question from acceptance to terminal outcome, not an entire conversation or Goal. New detail reporting prioritizes business responsiveness and may degrade with visible incompleteness; it does not promise zero Span loss. Run summaries need an independently defined statistical delivery and reconciliation contract before they can be described as complete.

This decision supersedes the SDK-based recommendation in the first-round draft only; it does not supersede existing tracing ADRs or change their contracts. See the [active design](../../.scratch/agent-observability/spec.md) and [decision record](../../.scratch/agent-observability/map.md).

On 2026-11-15 the user confirmed delivery as independent backend modules and APIs in SWE and independent Console pages, without adding a separately deployed service. A dedicated logger and bounded queue emit single-line JSON to stdout. Deployment-side collection is explicitly outside project scope, including its design, implementation, and acceptance. The user will manually arrange collection and ingestion; this project still owns the independent storage and index design, ingestion data contract, query/API implementation, and UI. Existing infrastructure alone does not select the new storage technology.

An Observability Run cannot reopen after a terminal outcome. Retries and approval continuation of the same non-terminal question retain that Run; a new question or execution after terminal completion gets a new Run and a predecessor association when applicable. Reconnecting does not create a Run. Content views accept the limits of existing NAS data and do not add content copies. Admission and terminal counts may read conversation and SubAgent business metadata; operation/performance statistics from logs must identify their observed coverage.

The third round confirmed that an Observability Attempt is one continuous execution within a Run: Agent-level re-execution and approval continuation create a new Attempt, while model retries and reconnects do not. Collection is default-off and selected once when a new Run is admitted; subsequent Attempts and SubAgents inherit that decision. Existing manager/admin role semantics apply to the new feature: a manager is restricted to the authorized Source, while an admin may explicitly query across Sources. The same authorized scope permits NAS body viewing without a separate body-role system; body reads still recheck ownership, deletion and redaction. This does not establish that arbitrary client role headers are trustworthy. Storage selection and the explicit no-cleanup scope are recorded in [ADR 0048](0048-independent-observability-metadata-uses-mysql.md).

The fourth round confirmed independent waiting_approval settlement despite the existing business Turn completing, unknown/partial rather than inferred failures when terminal facts are missing, and a metadata-only obs_context carried by approval and SubAgent launch records. There is one global collection switch, not Source-specific switches; per-Run snapshots still apply. P0 uses manual refresh and bounded polling. Identity and role resolution follow the project's existing mechanism; this feature does not introduce a new SSO, role issuer, signature validator or trusted-gateway prerequisite. New APIs still enforce the selected manager/admin Source scopes and NAS body authorization.

The consolidated implementation design is [2026-11-15 Independent Agent Observability](../superpowers/specs/2026-11-15-independent-agent-observability-design.md); implementation awaits final shared-understanding confirmation.
