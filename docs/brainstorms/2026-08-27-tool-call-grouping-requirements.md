# 工具调用分组展示

## Summary

将同一用户可理解任务阶段中的连续工具调用聚合为一个默认折叠的操作组。折叠态只展示经安全校验的组名和状态图标，用户点击后查看各个工具子步骤及其状态。

---

## Problem Frame

命令行操作和后台任务目前以独立工具卡片逐条展示。一次图片分析、文字识别或环境检查可能产生多次连续调用，导致对话中出现大量重复的“开始执行操作”，用户既难以判断这些调用是否属于同一阶段，也需要穿过大量技术过程才能继续阅读对话。

同时，工具调用可能包含命令、参数、路径和其他敏感信息。改善可读性不能依赖前端解析原始调用内容，也不能以展示更多底层细节为代价削弱现有安全边界。

当工具调用触发 Tool Guard 时，当前事件可能在工具尚未执行前就以失败型结果进入展示链路，使“等待审批”“用户拒绝”“策略拦截”和真正的工具执行失败看起来完全相同。这会误导用户，也会让操作组汇总状态失真。

---

## Actors

- A1. Console 用户：查看 Agent 的任务进展，并按需展开操作组了解子步骤状态。
- A2. Agent：为属于同一任务阶段的工具调用声明一致的操作组身份和用户可读组名。
- A3. 运行时与 Console：校验组名、维护组与子步骤状态，并以一致的折叠规则展示工具调用。

---

## Key Flows

- F1. 创建并更新操作组
  - **Trigger:** Agent 发起一个带有新操作组身份的工具调用。
  - **Actors:** A2, A3
  - **Steps:** Agent 提供组身份与组名；系统校验组名并在必要时安全降级；后续携带同一组身份的工具调用加入该组；正文消息、新组或 Agent 回合结束时结束当前组。
  - **Outcome:** 同一任务阶段的多个工具调用形成一个稳定操作组，各子步骤仍保留独立状态。
  - **Covered by:** R1, R2, R3, R4, R5

- F2. 折叠查看与按需展开
  - **Trigger:** Console 收到包含一个或多个子步骤的操作组。
  - **Actors:** A1, A3
  - **Steps:** Console 默认以折叠态显示组名和状态图标；用户点击组名后展开所有子步骤；用户可再次点击折叠。
  - **Outcome:** 工具过程默认不占用大量对话空间，但用户仍能按需查看每一步的状态。
  - **Covered by:** R6, R7, R8, R9

- F3. Tool Guard 治理状态更新
  - **Trigger:** 操作组中的工具调用触发 Tool Guard 审批或阻止策略。
  - **Actors:** A1, A2, A3
  - **Steps:** 系统将子步骤标记为待审批、已拒绝或已拦截；审批通过后恢复该步骤的执行状态；只有工具实际运行后报错才标记为执行失败。
  - **Outcome:** 用户能区分治理决策和执行结果，操作组不会把尚未执行的调用误报为失败。
  - **Covered by:** R17, R18, R19, R20, R21

## Requirements

**操作组声明与边界**

- R1. Agent 必须显式声明操作组；系统不得仅根据调用时间、相邻关系或工具类型自动推断新事件的分组归属。
- R2. 一个操作组必须对应一个用户可理解的任务阶段，而不是默认覆盖整个 Agent 回合或绑定是否存在执行计划。
- R3. 属于同一任务阶段的每个工具调用必须携带一致的操作组身份，并继续保留自身独立的工具调用身份、运行状态和结果。
- R4. 出现新的操作组、面向用户的正文消息或 Agent 回合结束时，当前操作组必须结束；已结束操作组不得吸收之后出现的工具调用。
- R5. Agent 可以自由填写用户可读组名，但系统必须将其视为不可信展示文本并执行确定性安全校验；校验失败时静默使用通用安全标题，不能阻断工具执行。

**折叠与展开行为**

- R6. 操作组无论处于执行中、待审批、治理警告、全部成功、执行失败或已经结束，都必须默认折叠。
- R7. 折叠态只展示组名和状态图标或颜色，不展示子步骤数量、状态文字、工具名称或结果摘要。
- R8. 状态不能只依赖颜色表达；在不增加状态文字的前提下，执行中、成功和失败必须具有可辨识的图标或等价非颜色提示。
- R9. 用户点击组名后，Console 必须展开该组的全部子步骤；用户再次点击后必须恢复折叠。用户的手动选择在当前页面生命周期内保持，不因后续状态更新而自动反转。

**子步骤文案与汇总状态**

- R10. `execute_shell_command` 子步骤必须按状态使用固定含义的文案：运行中显示“正在执行命令行操作”，成功显示“命令行操作已完成”，失败显示“命令行操作未成功”。
- R11. `start_background_process` 子步骤必须按状态使用固定含义的文案：运行中显示“正在启动后台任务”，成功显示“后台任务已启动”，失败显示“后台任务启动失败”。
- R12. 操作组的汇总状态必须由子步骤状态确定：存在运行中步骤时为执行中；所有步骤成功时为成功；任一步骤实际执行失败时为失败。Tool Guard 治理结果按 R20 单独汇总。
- R13. 后台任务成功启动即视为当前子步骤成功；后台进程之后停止或异常退出，不反向修改已经结束的操作组。

**安全与兼容边界**

- R14. 组名、折叠态和展开态均不得展示原始命令、参数、环境变量、绝对路径或未经后端认可的工具输出内容。
- R15. Console 不得解析原始工具参数来生成组名、子步骤标题或分组关系；展示所需的规范化语义必须由后端提供。
- R16. 缺少操作组身份的现有事件和历史事件继续按当前独立工具卡片方式展示，不进行自动聚合。

**Tool Guard 治理状态**

- R17. 工具调用等待 Tool Guard 审批时必须显示为“待审批”，不得标记为工具执行失败，因为工具此时尚未执行。
- R18. Tool Guard 审批通过后，子步骤必须从“待审批”恢复为运行中，并最终根据工具的真实执行结果进入成功或失败状态。
- R19. 用户拒绝 Tool Guard 审批时必须显示为“已拒绝”；策略不可审批地阻止工具时必须显示为“已拦截”。这两种状态均属于治理结果，不得复用工具执行失败状态。
- R20. 操作组存在待审批子步骤且没有真实执行失败时，汇总状态必须为待审批；操作组只有已拒绝或已拦截子步骤且没有真实执行失败时，必须显示治理警告状态；只有工具实际执行报错时，操作组才进入失败状态。
- R21. 折叠态必须为待审批和治理警告提供区别于执行中、成功及失败的状态图标；展开态必须显示“待审批”“已拒绝”或“已拦截”的明确文字，并且状态表达不能只依赖颜色。

**流式展示与执行过程收口**

- R22. Console 收到一个带有效操作组声明的首个工具调用时，必须立即渲染默认折叠的操作组，不能等待组内后续调用或全部工具结果返回。
- R23. 操作组展开后的工具步骤必须优先显示后端提供的调用动作摘要；结果摘要只在调用摘要缺失时作为兼容兜底，避免以“找到 N 项内容”等结果文案替代实际操作。
- R24. 一个操作组开始后、下一次同组工具调用前出现的 reasoning 消息必须按原始顺序保留在该操作组内；面向用户的正文、未分组工具或新组仍结束当前组。
- R25. 当响应完成并具备最终正文时，操作组必须作为一个整体进入既有“执行过程”折叠区域；响应仍在生成时，操作组保持直接可见且可展开。

## Acceptance Examples

- AE1. **Covers R1, R2, R3, R4.** 给定 Agent 连续执行“检查图片、识别文字、校验结果”三个工具调用，当三个调用声明同一操作组且随后输出正文时，Console 只形成一个已结束操作组，正文后的调用不会被加入该组。
- AE2. **Covers R5, R14.** 给定 Agent 提供的组名包含绝对路径、命令片段或疑似凭据，当系统校验该组名时，工具照常执行，操作组使用通用安全标题，敏感内容不进入展示事件。
- AE3. **Covers R6, R7, R8.** 给定执行中、成功和失败三种操作组，当页面首次渲染时，三者均保持折叠，只显示组名和各自可辨识的状态图标，不显示步骤数量或状态文字。
- AE4. **Covers R9, R10, R11.** 给定一个包含命令行操作和后台任务的折叠操作组，当用户点击组名时，Console 展开全部子步骤，并按工具类型和状态显示固定文案；再次点击后恢复折叠。
- AE5. **Covers R12.** 给定一个操作组包含两个成功步骤和一个失败步骤，当组状态更新时，折叠态显示失败图标；展开后用户能看到两个成功子步骤和一个失败子步骤。
- AE6. **Covers R13.** 给定后台任务已经成功启动，当操作组结束后该进程异常退出时，原操作组仍保持结束时的成功状态，不被追溯改写。
- AE7. **Covers R16.** 给定历史会话中的工具事件没有操作组身份，当 Console 回放这些事件时，每个事件仍按独立工具卡片展示，不因相邻或工具类型相同而自动合并。
- AE8. **Covers R17, R20, R21.** 给定一个工具调用触发 Tool Guard 审批，当用户尚未作出决定时，折叠操作组显示待审批图标而非失败图标；展开后对应子步骤显示“待审批”。
- AE9. **Covers R18.** 给定一个子步骤处于待审批状态，当用户批准执行时，该步骤恢复为运行中，并在工具结束后按真实结果显示成功或失败。
- AE10. **Covers R19, R20, R21.** 给定用户拒绝一个调用或策略自动拦截一个调用，当操作组没有真实执行失败时，折叠态显示治理警告图标；展开后分别显示“已拒绝”或“已拦截”，不得显示“命令行操作未成功”。
- AE11. **Covers R20.** 给定一个操作组同时包含已拦截步骤和一个实际执行失败步骤，当状态汇总时，真实执行失败优先，操作组显示失败状态；展开后仍分别保留“已拦截”和执行失败的子步骤状态。
- AE12. **Covers R22.** 给定流式响应刚收到一个带组声明、仍在运行且尚无结果的工具调用，当 Console 更新时，操作组标题立即出现并保持默认折叠。
- AE13. **Covers R23.** 给定工具调用摘要为“正在查找工作目录文件”且结果摘要为“共找到 1 项内容”，当用户展开操作组时，步骤显示调用摘要而不是结果摘要。
- AE14. **Covers R24.** 给定同一操作组内依次出现工具调用、reasoning、同组工具调用，当用户展开操作组时，三项按原始顺序展示；reasoning 不拆分操作组。
- AE15. **Covers R25.** 给定响应完成且已有最终正文，当 Console 收口执行过程时，操作组不再单独显示在正文旁，而是完整出现在“执行过程”折叠内容中。

## Success Criteria

- 多个属于同一任务阶段的工具调用在默认视图中只占用一个折叠条目，用户可以继续顺畅阅读对话。
- 用户能够通过组名和状态图标判断当前任务阶段及其总体状态，并可通过一次点击查看全部子步骤。
- 命令行操作与后台任务在展开态具有明确、稳定且不同的状态文案。
- 分组展示不扩大命令、参数、路径、环境变量或工具输出的暴露范围。
- Tool Guard 的待审批、已拒绝和已拦截状态不再被误报为工具执行失败，且审批与拦截能力本身保持不变。
- 流式阶段首个分组工具立即可见，组内 reasoning 与工具步骤保持原顺序；响应完成后整组进入执行过程折叠。
- 规划与实现无需重新决定分组粒度、默认展开策略、执行失败与治理状态的汇总规则、子步骤文案或历史事件行为。

---

## Scope Boundaries

- 不根据时间窗口、相邻关系、工具类型或前端启发式规则自动创建操作组。
- 不允许 Agent 为每个命令行或后台任务子步骤提供自由展示标题。
- 不对缺少操作组身份的历史事件执行回填、迁移或自动聚合。
- 不在折叠态展示步骤数量、状态文字、工具名称或结果摘要。
- 不展示原始命令、参数、路径、环境变量或完整工具输出。
- 不把后台进程启动后的长期运行状态纳入已结束操作组的生命周期。
- 不改变 Tool Guard 的检测、审批、拒绝、拦截或批准后重放能力；本需求只调整事件语义、状态汇总和 Console 展示。
- 不把已拒绝或已拦截视为成功，也不在没有用户批准时自动继续执行工具。

---

## Key Decisions

- 显式分组优先于自动推断：由 Agent 声明用户任务阶段，避免误合并无关调用。
- 组名自由表达、子步骤固定表达：组名提供用户语义，固定子步骤文案控制安全边界和一致性。
- 所有状态默认折叠：聚合首先服务于减少过程噪声，状态图标保留最低限度的可见性。
- 失败不自动展开：用户的展开选择优先，失败通过折叠态状态图标提示。
- 治理状态独立于执行状态：待审批、已拒绝和已拦截说明工具为何没有执行，只有运行后的报错才属于执行失败。
- 旧事件保持原样：兼容处理不能通过前端解析敏感参数来补造分组语义。
- 动作摘要优先于结果摘要：步骤名称回答“正在做什么”，结果状态与结果内容继续由状态和后端安全摘要表达。
- 操作组属于执行过程：生成中直接可见，响应完成后随其他过程内容统一折叠。

---

## Dependencies / Assumptions

- Agent 能为属于同一任务阶段的多个工具调用稳定复用同一操作组身份。
- 工具开始与结果事件能够继续关联为同一子步骤，并提供可归一化的运行、成功、执行失败和 Tool Guard 治理状态。
- Console 的状态图标具备执行中、待审批、治理警告、成功和执行失败等可辨识且无障碍可用的视觉表达。
