# 按来源扫描当日失败任务并补跑

## Summary

提供由外部调度平台调用的当日失败补跑能力，按来源异步扫描新版任务的最新有效失败，并逐项受理补跑。调用过程持久化、结果可追溯，补跑失败后可以继续纳入后续扫描，不设置业务补跑次数上限。

---

## Problem Frame

运维希望在外部调度平台手工注册一个周期任务，统一处理同来源用户当天失败的新版定时任务，减少逐用户、逐批次人工操作。当前已有针对指定批次成员的人工重试入口，但没有这个跨用户、按日扫描的业务入口。

失败历史并不一定仍需补跑：同任务可能已有更新的成功、排队或运行记录，批成员也可能尚在原有自动重试阶段。若只根据历史表的失败状态或 `is_final=1` 扫描，会产生提前补跑和重复执行。

---

## Actors

- A1. 运维：手工注册外部平台定时任务，查询调用批次及处理结果。
- A2. 外部调度平台：按自身配置频率调用接口，不由 Scheduler 自动注册这个平台任务。
- A3. Scheduler：记录调用、扫描筛选、受理入队、防重复、恢复处理及提供查询。
- A4. SWE：实际执行业务，更新同库运行状态、执行历史和任务运行态。

---

## Key Flows

- F1. 接口触发补跑
  - **Trigger:** A2 提交包含来源标识的请求。
  - **Actors:** A1、A2、A3。
  - **Steps:** 校验参数；保存调用记录及扫描截止时刻；立即返回调用批次标识；后台扫描并复核最新执行事实；逐项入队或记录跳过/失败；提供进度和结果查询。
  - **Outcome:** 一次调用有可查询的持久记录，符合条件的失败执行最多受理一条对应补跑；单项失败不阻断其余项。
  - **Covered by:** R1、R2、R5、R11、R12、R17、R18。

- F2. 执行与再次补跑
  - **Trigger:** A3 派发已入队的补跑，之后 A2 再次调用。
  - **Actors:** A2、A3、A4。
  - **Steps:** 使用最新任务定义；开始前检查是否已出现更新的调度成功结果；A4 开始及完成执行；新增历史并替换同链最终标识；维护运行态及原通知规则；新失败在下一次调用中重新评估。
  - **Outcome:** 不伪造业务完成，原失败可追溯；新的明确失败允许继续补跑，成功或不再满足执行条件的任务停止纳入。
  - **Covered by:** R6–R10、R13–R16。

---

## Requirements

**调用入口与记录**

- R1. 请求 Body 必填 `source_id`，扫描该来源下所有用户、所有 Agent 的新版定时任务；外部调度平台无需提供用户身份 Header，也不接受其指定任意执行正文。
- R2. 异步受理：先保存一条调用记录，再返回补跑批次标识；新建一张表保存受理后的接口调用、处理进度、统计、错误及恢复所需信息，并提供查询能力。
- R3. 按用户确认，不新增鉴权、调用凭证、角色限制或来源访问白名单；`source_id` 只用于数据筛选。保留参数校验、防重复受理、事务并发保护及审计，不能把筛选条件当作授权证明。
- R4. 每次受理调用均保留自己的记录；重复或并发调用不等于重复执行业务。参数校验拒绝、数据库不可用等未能受理的请求通过接口错误日志定位，不伪造已受理成功。

**扫描与候选资格**

- R5. “当日”按北京时间当天 00:00 至本次受理时刻，采用实际失败确认时间；异步子任务采用最终失败确认时间，不按原计划时间筛选。扫描截止时刻固定，受理后才新增的失败留给后续调用。
- R6. 仅包含新版普通调度、批调度及本接口补跑形成的执行链；用户点击“立即执行”等手动执行不参与候选和最新一轮判定。同一完整任务身份只看该链的最新一轮，本轮最多受理一次；最新成功、排队或运行中时不补旧失败。
- R7. 批父和批子都必须等待原有批自动重试结束且明确失败；只补失败成员自身，不重新触发或分发整个批次，不重跑成功成员。`is_final=1` 不能独立证明自动重试已结束。
- R8. 与批调度自动重试一致，排除认证过期类型 `auth_expired`，以及错误详情包含 `cron auth user_info is expired`、`workflow sapId does not match target user`、`技能任务结果不可用` 的失败；匹配不因英文大小写差异失效。
- R9. 跳过已删除、已停用、未读阈值自动暂停或不满足既有执行条件的任务；仅关闭批入口且成员自身仍可执行时允许补跑。不把派发未确认、执行失联或尚未收敛当作明确失败；确认结束的失败/超时再按重试规则判定。
- R10. 本接口的业务补跑次数与批内自动重试次数分开统计且不限次数，不另加业务冷却时间，由外部平台调用频率驱动。补跑的新失败允许再次扫描；跨日后新确认的失败可进入新一天扫描，但不得绕过 R6–R9 的跳过条件。

**补跑与数据状态**

- R11. 受理时使用当前最新任务定义生成新的 `swe_cron_execution_runs` 记录，复用既有执行队列与容量约束；保持任务 ID、会话绑定和原逻辑轮次，不修改原任务定义、排程或强制启停。
- R12. 在事务内复核任务和最新执行状态，以原失败执行为防重复依据；不能仅依赖进程内锁或调用方提供的请求 ID。同一失败已有补跑排队/执行时跳过，失败的新补跑记录则属于后续可重新评估的执行。
- R13. SWE 实际处理执行终态时，在 `swe_cron_executions` 新增历史；复用历史 `meta` 记录补跑来源、调用批次、根执行、上一次失败执行及补跑次数，不新增历史表列。运行记录也保留可追溯关联，调用记录与逐项补跑是一对多关系。
- R14. 任务运行态沿用同库正常执行链路更新：入队不伪写 running/成功、不提前清空上次结果；实际开始及结束由 SWE 更新状态、执行时间、错误与成功结果/未读等字段，不以较旧执行覆盖较新结果。Scheduler 不等待 SWE 通过另一个回执接口反馈结果。
- R15. 普通补跑和批成员补跑都维护同链 `is_final`：入队时旧历史暂为 1；新增历史时，在同一事务中把上一次历史置为 0、新历史置为 1；新失败保持 1 供后续评估。不能改动同任务其他调度周期的最终标识，不覆盖或删除原失败历史。
- R16. 补跑已入队后，若同任务出现更新的调度成功结果，尚未开始的旧补跑跳过；已开始的不中断。执行前仍遵循删除、停用等既有检查。是否最终成功必须考虑异步子任务收敛，不能只以主执行成功判断。

**通知、容错与边界**

- R17. 成功结果沿用原轮次的通知时点：未到时间则等待，时间已过则补发；正常生成报告、维护未读和原有自动暂停规则。补跑不是绕过未读自动暂停的入口。
- R18. 调用记录展示扫描、受理、跳过、逐项处理失败等统计，并能关联逐项补跑执行事实；扫描/入队结束不等于 SWE 全部执行结束，查询不得把两者混为“执行成功”。
- R19. 单项处理失败继续处理其他任务，调用记录能反映部分失败；服务重启后从数据库恢复未完成处理。失败原因有可定位日志，不输出 Cookie、Token、用户认证数据或完整任务正文。
- R20. 除一张调用记录新表外，逐项执行及结果复用现有运行表、执行历史和任务运行态，不另建一套业务结果存储。本次不整体合入此前 16 个本地提交；必要字段、索引、接口契约和既有能力适配进入实现设计核对，建表/更新 SQL 单独交付，不在启动时自动执行 DDL。

## Acceptance Examples

- AE1. **Covers R1、R3、R4.** 不带用户 Header 和调用凭证、Body 来源合法时可以受理；只扫描指定来源。来源缺失/非法时明确拒绝，不能无条件扫描全库。
- AE2. **Covers R5、R10.** 计划在今天但昨天已确认失败的记录不进入今天扫描；昨天开始、今天才确认失败的补跑可以进入今天扫描。受理后才失败的记录留给下一轮。
- AE3. **Covers R6、R12.** 同任务当天先失败后调度成功，旧失败不补；最新仍排队或运行也不补。手动执行成功或失败均不改变这条调度/补跑链的选择口径。
- AE4. **Covers R7.** 批成员仍有原生自动重试待处理时不补；已用尽原生重试且明确失败才可入队；父任务失败只重跑父任务自身，成功子成员保持原状。
- AE5. **Covers R8、R9.** 认证过期、workflow 目标用户不一致和技能结果不可用均跳过；没有明确失败结论的失联执行也不能强制重跑。
- AE6. **Covers R9、R17.** 任务已停用、删除或未读自动暂停时跳过；只有批入口暂停但成员可执行时可以受理。补跑成功后若达到原未读阈值，原暂停规则仍可生效。
- AE7. **Covers R10、R13.** 同链连续多次补跑失败且每次仍满足当天范围和资格时，超过三次也允许在后续调用中受理；次数和关联可追踪，不误用批内重试上限截断。
- AE8. **Covers R11、R12.** 任务定义在失败后被修改，补跑冻结修改后的定义。两次并发调用都留下调用记录，但同一失败只产生一个对应补跑，其余标记重复跳过。
- AE9. **Covers R13–R15.** 入队阶段不新增一条假完成历史，也不把旧历史提前置 0；实际新历史落库时原失败转为非最终，新记录为最终；其他轮次不变。
- AE10. **Covers R14、R16.** 补跑等待期间正常调度已经成功，尚未开始的旧补跑跳过；已开始则不中断。旧执行迟到结束不能覆盖较新的任务运行态。
- AE11. **Covers R16–R18.** 主执行成功但子任务未结束，查询不能宣称整轮成功；补跑结果在原通知时间之前完成时不提前通知，时间之后完成时补发。
- AE12. **Covers R2、R18–R20.** 一次受理的部分候选因异常未入队，其余继续；服务重启后可恢复并通过唯一关联避免再次入队。调用记录说明扫描处理是否完成，业务结果按执行事实查询。

## Success Criteria

- 运维只需在外部平台配置来源和周期，即可触发、查询、审计该来源的当日失败补跑。
- 不补历史上已被新成功覆盖的失败，不抢跑仍处于原生批重试阶段的成员，不重复受理同一失败。
- 每条实际补跑均有新运行及新历史，调用批次、补跑链、次数、运行态与最终标识可以相互核验。
- 重启、多次触发和单项异常不会让已受理补跑丢失或重复；原有队列、通知、未读及运行约束不被绕过。

---

## Scope Boundaries

- 不自动注册外部调度平台任务，不新增前端页面，不改旧任务执行和旧管理入口。
- 不新增鉴权/访问限制；任何能够到达接口的调用方都可触发指定来源全部用户的候选补跑。这是用户明确选择的暴露面，不应宣称 `source_id` 提供了授权保护。
- 不处理人工“立即执行”失败、旧任务和系统任务；不强制重跑结果未知或仍在执行的业务。
- 不安装或整体迁入既有批自动重试、存量迁移、系统任务迁移等此前本地提交中的功能。
- 本需求已获后续开发与测试授权；不自动提交、推送或执行外部数据库 DDL。

---

## Key Decisions

- 异步处理及持久化调用批次，避免外部平台 HTTP 请求等待整个来源扫描或实际业务执行。
- 最新一轮而非逐条历史失败：减少重复产出；人工调试不改变自动补跑链口径。
- 不限次数且允许跨日：新失败持续满足条件时可以持续补跑；成功、暂停和明确排除条件会阻止继续受理。
- 新增历史而不覆盖失败，`is_final` 标识同链最新尝试，不表示重试已耗尽、执行已停止或业务已成功。
- SWE/Scheduler/Monitor 共用数据库；Scheduler 负责受理与扫描，SWE 负责执行结果写入，不新增结果回传链路。

---

## Dependencies / Assumptions

- 工作基线为干净的 `codex/cron-ui-fixes-only`，基于远端 `v1.0.0`，不采用本地 `v1.0.0` 的额外 16 个提交为开发父历史。
- 当前干净基线存在人工批重试，但没有 `scheduler/src/scheduler/app/services/cron/managed/auto_retry.py`；此前本地 `v1.0.0` 中的实现只作为已确认重试排除规则的参考，不能直接整批合入。
- 行内原有批自动重试继续作为既有能力。实现设计必须识别“原生重试已经结束”的可靠事实；若当前记录不足以判定，应明确跳过并报告原因，不能把一次中间失败当最终失败。必要的兼容适配应单独纳入本功能设计。
- 历史已有 `meta`、运行记录已有执行关联，落标优先复用；数据库实际版本、索引和恢复策略在实现设计中核对。

## Outstanding Questions

### Resolve Before Planning

无待确认的业务选择；用户已确认全部筛选、通知、容错口径，并明确不需要访问限制。

### Deferred to Planning

- [Affects R2、R18–R20][Technical] 确定调用表字段、查询接口契约、索引和手工执行 SQL。
- [Affects R5–R12、R16][Technical] 核验实际失败时间、最新执行、批原生重试结束及执行前失效的可靠判定，保留现有锁顺序和并发约束。
- [Affects R11–R15][Technical] 设计来源级后台处理、逐项入队防重、重启恢复、普通/批成员历史替换及状态写入的最小兼容改造。
- [Affects R13–R17][Technical] 核验历史 meta 容量与必要关联不被截断、异步最终结果、未读和通知在补跑中的一致性，并形成针对性测试。
