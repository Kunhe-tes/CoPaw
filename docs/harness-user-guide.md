# Harness 用户说明

## 什么是 Harness

Harness 是包在 AI 模型外层的一套运行系统。模型负责理解和生成内容，Harness 负责把模型接到真实工作环境中，并管理它什么时候调用工具、什么时候继续、什么时候停下、如何保留记忆、如何接受安全检查，以及如何把执行过程展示给用户和管理员。

可以把 Harness 理解为 AI Agent 的“操作系统 + 护栏 + 仪表盘”：

- 操作系统：连接文件、终端、工具、MCP、定时任务、工作区和前端会话。
- 护栏：控制权限、审批高风险操作、限制上下文膨胀、隔离租户数据。
- 仪表盘：记录执行、Dream 治理、Token、Tracing、Hook telemetry 和可回滚结果。

在本项目中，Harness 不是一个单独模块，也不只等于 Console 里的 Harness 页面。它由请求编排、AgentLoop、ToolGuard、Hook Runtime、Memory、SubAgent、Dream、定时任务、Tracing 和 Console 可视化页面共同组成。

## Harness 覆盖的能力

| 能力层 | 普通用户视角 | 当前项目中的内容 |
|--------|--------------|------------------|
| 工具与环境 | Agent 可以读写文件、搜索文件、执行命令、调用时间/Token/任务进度等工具 | 内置工具、MCP 工具和工作区上下文共同组成工具环境 |
| 上下文与记忆 | Agent 能记住会话、检索长期记忆，并在上下文过长时压缩历史 | 会话记忆、长期记忆、记忆检索、上下文压缩和工具结果截断 |
| 编排调度 | 系统决定一轮对话如何进入模型、工具、继续执行和停止 | 请求编排、ReAct AgentLoop、停止前检查和结果保存 |
| 任务分派 | 主 Agent 可以把独立子任务交给 SubAgent 后台执行 | 后台 SubAgent、运行监控、取消、精简结果回传 |
| 状态与恢复 | 会话、任务、Dream 记录、备份和中间状态会落盘或写入数据库 | 会话历史、任务状态、Dream 记录、治理记录和运行快照 |
| 验证评估 | 停止前可通过 Hook 做完成度检查，工具输出可被规则或 Prompt handler 审查 | `BeforeStop` / `Stop` Hook、ToolGuard、Prompt Hook |
| 治理安全 | 高风险工具需要审批或被拒绝，租户目录和密钥隔离，技能进入前可扫描 | 工具审批、租户隔离、路径边界、SubAgent 策略和 Hook 权限决策 |
| 可观测性 | 管理员可查看执行记录、治理结果、Hook telemetry、Tracing 和 Token | Console Harness 页面、Tracing、Token Usage、`HOOK_TELEMETRY` 日志 |

## 一次请求如何经过 Harness

用户发起一条消息后，典型链路如下：

```text
用户输入
  -> Runner 接收请求并绑定 tenant/source/session 上下文
  -> 可触发 UserPromptSubmit Hook
  -> 主 Agent 进入 AgentLoop
  -> 模型思考下一步
  -> 如果需要工具，先经过 ToolGuard 和 PreToolUse Hook
  -> 工具执行，结果进入会话记忆
  -> 如果任务适合拆分，可启动后台 SubAgent 并持续查看其状态
  -> PostToolUse 或 PostToolUseFailure Hook 可补充上下文或拦截问题
  -> Agent 继续模型/工具循环，直到准备回答
  -> BeforeStop Hook 可检查是否真的完成
  -> Stop Hook 做收尾
  -> Runner 保存会话状态、追加任务进度、Tracing 和建议内容
```

这条链路说明：用户看到的是一段回答，但背后 Harness 可能已经完成了上下文加载、工具治理、自动续跑、记忆压缩和可观测性记录。

## Hook：关键节点上的自动检查与动作

Hook 是 Harness 在关键时间点自动执行的小流程。它可以用于安全检查、补充上下文、调用外部系统、要求人工审批，或在 Agent 准备结束时检查任务是否真的完成。

当前支持的 Hook 事件包括：

| 事件 | 触发时机 | 典型用途 |
|------|----------|----------|
| `SessionStart` | 会话开始或恢复时 | 初始化上下文、加载会话级策略 |
| `UserPromptSubmit` | 用户消息提交后、Agent 正式执行前 | 检查输入、补充系统上下文、阻断不合规请求 |
| `PreToolUse` | 工具执行前 | 工具权限审查、改写工具输入、请求人工确认 |
| `PostToolUse` | 工具成功后 | 根据工具输出补充上下文、写入审计信息 |
| `PostToolUseFailure` | 工具失败后 | 给出失败兜底提示、追加修复建议 |
| `BeforeStop` | Agent 准备结束前 | 判断任务是否完成；必要时阻止停止并自动续跑 |
| `Stop` | 一轮请求最终结束时 | 收尾、追加结果上下文、通知外部系统 |

Hook handler 有三类：

- `command`：执行本地命令或脚本。
- `http`：调用外部 HTTP 服务。
- `prompt`：用模型做结构化判断，返回 allow/block/deny 等结果。

Hook 的结果会被统一合并。它可以产生：

- `allow`：允许继续。
- `ask`：要求用户或管理员确认。
- `deny` / `block`：阻断当前动作。
- `stop`：停止当前流程。
- `additionalContext`：把额外上下文写回本轮记忆，让 Agent 后续能看到。
- `updatedInput`：改写工具输入。

特别说明：

- `BeforeStop` 是当前项目里最接近“自动验收”的节点。它如果返回 `block`，Runner 会在预算内自动追加一轮内部续跑，让 Agent 继续补完任务。
- `BeforeStop` 默认自动续跑预算是 2 轮；也可通过 `running.hook_runtime.max_before_stop_turns` 或兼容字段配置。
- Hook 可以按 handler 开启会话快照，但快照默认最多 50 条，硬上限 200 条，并且不包含 reasoning 内容，避免把完整隐私上下文暴露给所有 Hook。
- Hook telemetry 会以 `HOOK_TELEMETRY ` 前缀写入日志，用于排查 Hook 是否执行、是否阻断、耗时多少；它不写入 tracing span。

## Memory：短期上下文、长期记忆与自动压缩

Memory 是 Harness 的上下文层。它解决两个问题：

1. 当前会话中，Agent 需要知道之前说过什么、工具返回过什么。
2. 长期使用中，Agent 需要保存稳定经验、偏好、业务规则，同时避免上下文无限变长。

当前项目中 Memory 包括：

| 能力 | 说明 |
|------|------|
| 会话记忆 | 当前对话中的用户消息、助手消息、工具调用和工具结果 |
| 长期记忆 | 长期记忆区和每日记忆日志里的稳定信息 |
| 记忆检索 | `memory_search` 工具可按语义检索过往记忆，返回相关片段和路径 |
| 上下文压缩 | 上下文接近阈值时，`MemoryCompactionHook` 会压缩旧消息并保留最近消息 |
| 工具结果截断 | 大工具输出会保留近期较长内容，历史结果会压缩或转入独立保存区 |
| 异步总结 | 部分旧消息可进入后台 summary 任务，减少主流程等待 |
| 租户隔离 | 每个 tenant 的 memory 目录独立，不共享 API Key、模型配置或记忆文件 |

Agent 在正常回复前会设置当前工作区、工具结果截断阈值、文件读取阈值和任务进度上下文。如果启用了 Memory Manager，Agent 会注册 `memory_search`，并在需要时强制检索长期记忆，把结果注入本轮上下文。

用户能感知到的现象：

- 问到过去的偏好、决策、日期、待办时，Agent 可以先检索记忆再回答。
- 工具输出特别大时，回答中可能出现 `<<<TRUNCATED>>>`，表示完整内容已保留但上下文里只放了摘要或前缀。
- 长会话中，旧内容会被压缩成摘要，减少模型遗忘或超上下文风险。

## AgentLoop：模型、工具和停止边界的主循环

AgentLoop 是 Harness 的编排层。它负责让 Agent 在“模型思考”和“工具执行”之间循环，直到生成最终回答。

当前项目使用 ReAct 风格的循环：

```text
模型判断下一步
  -> 如果需要工具，生成 tool_use
  -> Harness 审查工具调用
  -> 工具执行并返回 tool_result
  -> 工具结果写入 memory
  -> 模型继续判断
  -> 直到模型输出最终回答
```

项目里的主 Agent 在这个循环外还补充了几层能力：

- 根据 Agent 配置启用或禁用内置工具。
- Plan Mode 下只允许规划和只读工具。
- SubAgent 下按子 Agent 策略限制可用工具和工具调用预算。
- 工具执行前后进入 ToolGuard、Hook、Tracing 和审批流程。
- 对不支持多模态的模型，自动剥离不兼容的媒体块后重试。
- 每轮回复时设置工作区、文件读取和工具结果压缩配置。
- Runner 在流式输出外层补充 trace_id、任务进度和 reasoning 边界规范化。

这意味着 AgentLoop 不只是“反复问模型”。它还承担了失败重试、工具治理、状态保存、停止前验收和可观测性衔接。

## SubAgent：把独立子任务交给后台 Agent

SubAgent 是 Harness 里的任务分派能力。主 Agent 遇到适合并行或独立处理的工作时，可以启动一个后台 SubAgent，让它在受限环境中完成子任务，再把精简结果返回给主对话。

普通用户可以把 SubAgent 理解为“被主 Agent 临时叫来处理专项工作的助手”。它适合做这些事情：

- 独立调查一个范围明确的问题。
- 并行处理不需要主 Agent 持续盯着的任务。
- 在主对话继续推进时，后台收集证据、生成摘要或给出风险提示。
- 把复杂任务拆成主线和支线，避免主对话上下文被过多细节淹没。

当前 SubAgent 的关键特征：

| 能力 | 说明 |
|------|------|
| 后台运行 | SubAgent 以后台运行方式执行，主 Agent 可以启动、等待、查询或取消它 |
| 运行隔离 | SubAgent 使用独立运行上下文，避免直接污染主 Agent 的会话记忆 |
| 精简回传 | 默认只把运行身份、状态和紧凑结果返回给主 Agent，不把完整日志塞回主对话 |
| 策略限制 | SubAgent 有独立工具权限、预算和只读策略，不能随意扩大自己的权限 |
| 禁止嵌套委派 | SubAgent 不应再继续创建新的 SubAgent，避免任务树失控 |
| 定义匹配 | 系统可以复用已保存的 SubAgent 定义；如果没有合适定义，则创建本次运行专用定义 |
| 状态监控 | Chat 侧可以看到当前会话相关的 SubAgent 运行快照，包括状态、耗时预算和错误摘要 |
| 直接取消 | 用户可从监控入口取消某个后台 SubAgent，不依赖主 Agent 再发自然语言指令 |

SubAgent 与 Hook、Memory、ToolGuard 的关系：

- SubAgent 启动本身属于工具能力，会进入工具治理和审批边界。
- SubAgent 内部工具调用仍会受到自身权限策略和预算约束。
- SubAgent 默认不共享主 Agent 的完整记忆，也不把完整运行材料自动塞回主上下文。
- 主 Agent 看到的是面向父任务的结果投影：成功/失败、关键结论、简短摘要、必要风险。

用户能感知到的现象：

- 对话中可能出现后台 SubAgent 正在运行的监控卡片。
- 主 Agent 可能先继续处理主线，稍后等待或读取 SubAgent 的结果。
- 如果 SubAgent 超时、失败或被取消，主 Agent 会拿到简短错误摘要，而不是完整内部日志。
- 监控卡片里的进度更接近“时间预算消耗”，不是严格的任务完成百分比。

## Dream：长期记忆的后台整理与持续治理

Dream 是本项目里 Harness 的长期自维护机制。它不是用户对话中的普通回复，而是一个后台整理任务，用于定期或手动优化长期记忆和系统上下文文件。

Dream 会做什么：

1. 读取长期记忆与当日记忆日志。
2. 读取 Agent 的关键身份、行为准则和档案上下文。
3. 在修改前把相关上下文文件保存到备份区。
4. 使用一个专门的 `DreamOptimizer` Agent 整理内容。
5. 只做去重、合并、删除过期内容、保留高价值经验，不重写真实 Agent 的身份。
6. 记录执行结果、耗时、模型、Token、修改文件和摘要。
7. 支持查看 Diff、单文件回滚或整次回滚。

Dream 有两种触发方式：

- 手动触发：Console Harness 页面点击“立即触发”，后端异步执行。
- 定时触发：外部调度平台按配置回调后自动执行。

Dream 记录会写入工作区治理记录，并可同步到持续治理读模型。Console 页面可以查看：

- 总执行次数、成功率、节省空间、修改文件数、平均耗时、最近优化时间。
- 每次执行的时间、触发方式、状态、耗时、修改文件和摘要。
- 单文件 Diff、单文件回滚、整次回滚。
- 备份文件、孤儿文件清理、归档治理。

## Console 中的 Harness 页面

当前 Console 的 `Harness` 页面实际挂载的是“持续迭代”页面，重点展示 Dream 和治理结果。

主要能力：

| 页面能力 | 用户能做什么 |
|----------|--------------|
| 治理记录 | 查看 Dream 执行历史、成功/失败状态、触发方式和耗时 |
| 手动触发 | 立即启动一次 Dream 优化 |
| 运行状态 | 看到正在执行的治理任务，前端每 2 秒轮询一次状态 |
| 筛选 | 按日期、状态、触发方式筛选记录 |
| Diff 查看 | 查看某次 Dream 对文件做了哪些变化 |
| 回滚 | 对单个文件或整次 Dream 结果回滚 |
| 备份 | 查看 Dream 前生成的备份文件 |
| 清理 | 管理孤儿文件和可清理文件 |
| 归档治理 | 管理员可查看归档、恢复、保护和清理记录 |

因此，对普通用户来说，Console Harness 页面主要是“长期治理与回滚入口”。Hook、AgentLoop、ToolGuard、Memory、SubAgent 和请求编排共同构成 Harness 的核心执行能力，但这些能力不一定都集中展示在同一个页面里。

## 安全与治理如何生效

Harness 的安全能力主要体现在工具调用和数据边界上：

- 高风险工具会进入 ToolGuard，例如 Shell、文件读写、浏览器等。
- ToolGuard 可以直接拒绝危险操作，也可以生成审批请求。
- Hook 的 `permissionDecision` 可以和审批流程联动，例如 `ask` 用户确认后再重放工具调用。
- Plan Mode 只允许规划和保守只读命令。
- SubAgent 有独立的工具白名单和工具调用预算。
- 租户目录、密钥目录、模型目录、记忆目录按 tenant 隔离。
- Shell 和 MCP stdio 子进程可受 tenant 级 CPU/内存限制。
- 技能文件进入系统前可经过扫描器检查风险模式。

这些机制的目标不是让 Agent “不能工作”，而是在真实文件、命令、数据库和外部服务面前，给每一次高风险动作加上可解释、可审批、可追踪的边界。

## 当前边界与注意事项

- 历史上的“回答后校验 -> 自动续跑”功能已退役；当前主要由 `BeforeStop` Hook 承担停止前检查。
- Hook telemetry 是日志事件，不是 tracing span；排查 Hook 时需要看 `HOOK_TELEMETRY ` 日志前缀。
- Dream 会修改记忆和上下文文件，所以它总是先做备份，并提供 Diff 与回滚。
- 工具结果截断不代表完整结果丢失，通常表示完整内容被落盘或历史上下文被压缩。
- SubAgent 适合边界清晰的后台子任务；如果任务必须持续和用户交互，仍应由主 Agent 直接处理。
- Harness 页当前主要展示 Dream/持续治理，不覆盖所有 Hook、ToolGuard、SubAgent、Tracing 细节。
