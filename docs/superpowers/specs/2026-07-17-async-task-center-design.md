# 异步任务中心与接口异步化设计文档

## 摘要

把当前几个耗时较长的写操作改造成统一的异步任务，并提供一个可查询历史的任务中心页面。

本次覆盖的任务来源包括：

- 定时任务分发
- 技能分发
- MCP 分发
- 租户初始化

目标不是把业务逻辑改写成新的服务，而是把“受理请求”和“执行任务”分开，让前端可以稳定查询状态、失败原因和历史记录。

## 目标

- 统一异步任务协议。
- 四类长耗时接口立即返回任务 ID，不再阻塞到结果完成。
- 任务状态可被页面查询，且历史可保留。
- Console 提供一个统一的“异步任务中心”页面。
- 保持现有业务权限、租户隔离和结果语义不变。

## 非目标

- 不重写技能、MCP、Cron 或租户初始化的核心业务逻辑。
- 不引入新的独立调度服务。
- 不做跨服务分布式消息队列改造。
- 不把所有后台动作都强行纳入一个全局数据库表。

## 总体方案

采用“各服务本地执行 + 统一任务协议 + Console 聚合查询”的方式。

- `swe` 负责 Cron 与租户初始化相关任务。
- `market` 负责技能与 MCP 分发任务。
- 每个服务都持有自己的任务持久化存储，保存任务历史和任务明细。
- Console 通过统一任务 API 聚合不同服务的任务列表与任务详情。
- 如果分发目标尚未完成 bootstrap，则 bootstrap 也作为同一个异步任务的一部分执行，不再在请求线程里同步等待。

这样可以做到：

- 任务状态有持久化历史。
- 各服务仍然保留自己的部署边界。
- 新任务类型以后可以按同一协议继续接入。

## 任务模型

### 统一字段

所有异步任务都使用同一套核心字段：

```json
{
  "task_id": "uuid",
  "task_type": "market.skill.distribute",
  "service": "market",
  "status": "running",
  "title": "分发技能",
  "summary": "已处理 12 / 30 个租户",
  "progress": {
    "total": 30,
    "done": 12,
    "failed": 1
  },
  "actor_user_id": "u10001",
  "actor_user_name": "张三",
  "source_id": "default",
  "tenant_id": "default",
  "target_count": 30,
  "error_message": null,
  "result": {},
  "created_at": "2026-07-17T08:00:00Z",
  "updated_at": "2026-07-17T08:02:00Z",
  "finished_at": null
}
```

### 状态枚举

统一使用以下状态：

- `queued`
- `running`
- `succeeded`
- `failed`
- `partial_failed`

说明：

- `queued` 表示任务已受理，尚未开始执行。
- `partial_failed` 用于“部分目标成功、部分目标失败”的批量任务。
- `failed` 用于任务级异常或完全失败。

### 任务类型

建议固定以下 `task_type` 取值：

- `cron.broadcast`
- `market.skill.distribute`
- `market.mcp.distribute`
- `tenant.bootstrap`

### 任务结果

不同任务的 `result` 保持业务自描述，但外层结构统一。

- Cron 分发任务：保留目标租户结果、失败摘要和统计计数。
- 技能分发任务：保留分发数量、冲突明细和失败租户。
- MCP 分发任务：保留分发数量、冲突明细和失败租户。
- 租户初始化任务：保留是否已 bootstrap、初始化阶段和异常摘要。

## API 设计

### 任务受理接口

四类原有长耗时接口改为返回任务受理结果。

#### 定时任务分发

当前的 Cron 分发相关接口改为异步受理，返回：

```json
{
  "task_id": "uuid",
  "status": "queued",
  "reused": false
}
```

#### 技能分发

`POST /market/skills/{item_id}/distribute`

#### MCP 分发

`POST /market/mcp/{item_id}/distribute`

#### 租户初始化

凡是会触发 `TenantInitializer.ensure_seeded_bootstrap()` 的用户可见初始化入口，改为异步任务。

### 任务查询接口

每个服务都提供一致的任务查询 API：

- `GET /tasks`
- `GET /tasks/{task_id}`

其中 `GET /tasks` 支持按以下条件过滤：

- `service`
- `task_type`
- `status`
- `source_id`
- `tenant_id`
- `actor_user_id`
- `keyword`
- `created_from`
- `created_to`

Console 任务中心通过这些接口聚合 `swe` 和 `market` 的任务列表。

### 任务幂等

对于相同业务键的重复提交，若已有同类型任务正在运行，可以返回同一个 `task_id`，避免重复执行。

业务键建议包括：

- 任务类型
- 来源租户或来源 ID
- 目标集合
- 操作者
- 对象 ID

## 执行流程

### 1. 受理阶段

1. 前端提交异步操作。
2. 后端验证权限、参数和目标对象存在性。
3. 后端创建持久化任务记录，状态为 `queued`。
4. 后端立即返回 `task_id`。

### 2. 执行阶段

1. 后台 worker 把状态切到 `running`。
2. 任务执行原有业务逻辑。
3. 批量任务逐目标写入明细。
4. 任务完成时写入最终状态和结果。

### 3. 查询阶段

1. Console 任务中心按条件拉取任务列表。
2. 用户点开某条任务后查询详情。
3. 对运行中的任务，前端定时刷新当前行或详情面板。

## Console 设计

### 页面

新增一个统一页面，建议路由为 `/async-tasks`。

页面采用列表 + 详情的管理页形态：

- 顶部筛选条：任务类型、状态、服务、时间范围、关键词。
- 左侧主列表：任务名称、类型、服务、状态、进度、创建时间。
- 右侧详情区：任务 ID、操作者、来源、统计、错误摘要、结果明细。

### 页面行为

- 提交任务后，在原页面提示“任务已受理”，并提供跳转任务中心的入口。
- 任务中心默认展示最近任务和当前运行中的任务。
- 单条任务支持自动轮询，直到状态终态。
- 历史任务可通过任务 ID 精确查询。

### 视觉要求

- 采用现有 Console 白底管理台风格。
- 任务状态使用清晰徽标，不只靠颜色区分。
- 长任务 ID、长租户名和长错误文本必须支持截断与展开。

## 后端落点

### SWE

- Cron 分发任务异步化。
- 租户初始化任务异步化。
- 新增任务存储、任务查询与任务详情接口。

### Market

- 技能分发任务异步化。
- MCP 分发任务异步化。
- 新增任务存储、任务查询与任务详情接口。

### Console

- 新增任务 API 适配层。
- 新增任务中心页面。
- 更新现有分发页面的提交反馈和轮询逻辑。

## 错误处理

- 参数错误：直接返回 `400`。
- 权限不足：沿用现有权限错误。
- 目标对象不存在：返回 `404`。
- 任务受理失败：返回 `503 Service Unavailable`，不创建半残任务。
- 任务执行失败：任务状态置为 `failed`，保留错误摘要和部分结果。

对于批量任务，只要存在部分成功部分失败，就必须保留所有已完成的子结果，并把状态置为 `partial_failed`。

## 历史保留

任务记录默认保留，不在本次变更中做自动删除。

后续如果需要清理策略，应单独设计保留周期和归档流程，避免影响任务中心的历史查询能力。

## 测试策略

### 后端

- 任务受理后立即返回 `task_id`。
- 任务执行过程中状态能正确流转。
- 批量任务的成功、失败和部分失败统计正确。
- 历史查询接口可以取回已完成任务。
- 重复受理能按业务键复用运行中的任务。

### 前端

- 分发接口的返回类型从同步结果改为任务受理结果。
- 任务中心能列出任务、筛选任务并打开详情。
- 运行中任务能轮询刷新。
- 失败任务能展示错误摘要和结果明细。

## 风险与约束

- 如果某个服务的任务存储不可用，异步化接口会更早失败，这是有意为之，因为历史查询比“先执行后说”更重要。
- 由于任务分布在两个服务，Console 需要聚合查询，不能假设单一后端就能拿到全部数据。
- 现有同步调用方必须同步改造，否则会把“任务已受理”误当成“任务已完成”。
