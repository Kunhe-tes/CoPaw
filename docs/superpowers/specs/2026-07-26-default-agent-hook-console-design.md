# Default Agent Hook Console Design

## Goal

Replace manual editing of the Default Agent Profile Hook configuration with a dedicated Run Center console. The console manages the complete existing Hook model, a controlled Default Agent Profile script library, best-effort structured audit logs, and manual testing of draft handlers.

The first release is deliberately scoped to the tenant's `default` Agent Profile. It does not introduce an Agent selector or a separate manager/admin role requirement.

## Architecture

The console is a new **Run Center / Hook Management** page with three areas:

1. **Configuration**: the Hook configuration editor.
2. **Script library**: Default Agent Profile-owned script assets.

The console does not display audit history in the first release. It tells users that audit events are emitted to the application log system.

The backend exposes dedicated Hook-management APIs rather than extending the generic Agent API. They load and update only the `hooks` field of the `default` Agent Profile's `agent.json`, then use the existing non-blocking Agent reload mechanism after a successful save.

The existing Hook models, validation, resolver, executor, and telemetry remain the execution source of truth. The new APIs add UI-oriented validation, script-library ownership checks, ETag conflict detection, batch-upload handling, manual-test orchestration, and structured audit-log emission.

## Configuration Editor

The Configuration area uses a master-detail layout.

- The left tree represents the existing hierarchy: event → matcher group → handler.
- The right pane edits the selected event, matcher group, or handler.
- The global Hook enabled switch is visible at the Configuration root.
- Handler and matcher-group IDs are generated by default, remain editable, and must be globally unique throughout the configuration.
- Handler and matcher-group removal affects the draft only; a successful save removes them from later Hook resolution without deleting any script asset.

All fields supported by the existing `HookConfig` model are available. Common fields are directly visible; the condition expression, timeout, failure policy, once behavior, conversation snapshot fields, status message, command working directory/environment, and HTTP authentication fields live in an expandable advanced section.

The editor supports `command`, `http`, and `prompt` handlers. Command handlers use a free-form ordered `argv` array and must not use the shell-command string field. The UI must preserve model constraints such as prompt-handler event eligibility and unsupported command async settings.

## Script Library

Scripts belong only to the Default Agent Profile and are stored under its controlled `hooks/scripts/` workspace directory.

- Accepted extensions: `.py`, `.sh`, `.bash`, `.zsh`.
- Per-file limit: 1 MB.
- Per-batch limit: 20 files.
- Batch processing is per file: a failed file does not roll back successful files.
- Script deletion is unavailable in the first release.
- A same-name upload replaces the stored content after explicit confirmation, records both old and new SHA-256 values, and affects only later Hook events.
- Every uploaded or replaced file is evaluated with the existing scanner's configured `off`, `warn`, or `block` policy.

Any `argv` entry that is a script reference must resolve to an owned uploaded script. The API canonicalizes the reference and rejects absolute paths, parent-directory traversal, and scripts elsewhere in the workspace. Executable programs and ordinary non-script arguments remain free-form, including `argv[0]`.

## Save, Activation, and Concurrency

The editor holds a client-side draft. A save validates the complete configuration, updates only the Hook portion of `agent.json`, and schedules the existing asynchronous reload.

Uploaded or replaced scripts are persisted immediately. Configuration changes become active only after save and reload. An already-running Hook continues with its previous configuration and script content; later Hook events resolve the new state.

The complete Hook configuration has an ETag revision. Saves must provide the revision used to create the draft. A mismatched revision returns a conflict rather than silently overwriting another user's changes. Script replacement keeps the explicit confirmation and audit behavior but is not governed by the configuration ETag.

## Manual Test

Each handler detail pane offers a Manual Test action for the current draft handler.

- The user selects or edits an event-appropriate sample HookContext.
- The action requires explicit confirmation because it performs the selected handler's real command execution, HTTP request, or prompt-model invocation.
- It executes exactly one draft handler, not all handlers in a matcher group.
- It does not persist the draft, reload the Agent, or update the `once` state.
- The response contains only a redacted and bounded result summary.

## Structured Audit Logs

No new audit database table or audit-history console view is introduced. Operations emit best-effort structured application logs using a stable `agent_hook.audit` event name/prefix.

Events cover configuration saves, uploads, replacements, Handler/group removal, manual-test requests, and manual-test completion or failure. Their payload contains actor identity, action, time, Default Agent Profile identity, configuration revision where applicable, script name, old/new digest where applicable, scan outcome, duration, and redacted bounded summaries.

The log payload never includes script content, complete HookContext values, secrets, HTTP Header values, or unbounded stdout/stderr. Logging failures produce an internal warning but do not block the corresponding action.

## API and Failure Behavior

Dedicated APIs provide configuration read/save, script list/upload, and manual test. Audit events are emitted through the application log system rather than queried through a Hook-management API.

- Configuration saves validate the existing Pydantic Hook model plus console-specific uniqueness, path, and ETag requirements before writing or scheduling reload.
- Upload results distinguish accepted, warned, rejected, and failed files individually.
- Manual tests reject invalid draft handlers before confirmation or execution.
- Normal tenant-scoped access rules apply. The console adds no manager/admin role gate.

## Verification

Backend tests cover tenant isolation, default-Agent-only targeting, complete model validation, Handler/group ID uniqueness, ETag conflicts, path traversal rejection, script upload limits and replacement, all scanner modes, reload scheduling, manual-test state isolation, output redaction, and audit-log payload redaction.

Frontend tests cover the master-detail tree, full-field forms and advanced settings, error display, conflict recovery, per-file upload status, replacement/test confirmations, and the audit-log guidance notice.
