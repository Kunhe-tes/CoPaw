# 会话压缩历史可见性设计

## 目标

让用户能够明确感知上下文压缩，并在聊天界面向上滚动时按需查看被压缩前的原始消息。

本变更优先解决体验问题，不改变模型侧的压缩阈值、摘要策略或长期记忆生成策略。

## 现状与问题

`MemoryCompactionHook` 在压缩成功后调用 `mark_messages_compressed()`：原始消息被写入 ReMe 的 `dialog/YYYY-MM-DD.jsonl`，随后从在线 memory 移除。当前聊天详情接口只读取 session state 中的在线 memory，因此：

- 聊天界面没有压缩边界提示；
- 被压缩的历史无法在 UI 中查看；
- 现有归档以日期而非会话组织，不能安全地按聊天查询。

## 决策

归档目录改为以聊天 ID 隔离；每次成功压缩写入一个不可变批次文件：

```text
dialog/
  <chat_id>/
    manifest.json
    <boundary_id>.jsonl
```

原始消息只写入上述 JSONL 文件，不保存第二份消息副本。`manifest.json` 仅保存压缩边界元数据。

### 为什么不用共享的日期文件

当前 ReMe 写入的每行只是 `Msg.to_dict()`，不含 `chat_id` 或可供可靠筛选的会话标识。不同聊天会混入同一天文件；在读取时扫描并推断归属会造成串会话风险。因此写入阶段必须使用请求上下文中的 `chat_id` 选择归档目录。

## 数据模型

每次成功压缩新增一个边界记录，至少包含：

- `id`：稳定的边界 ID；
- `created_at`：压缩完成时间；
- `archived_message_count`：本次归档的展示安全历史消息数，不是最终 UI 卡片数；
- `first_message_id`、`last_message_id`；
- `first_timestamp`、`last_timestamp`；
- `status`：仅成功写入后为 `completed`。

边界记录按时间排序。它不保存摘要正文，也不保存消息副本。

## 写入流程

1. Runner 已把 `chat_id` 写入 Agent 的请求上下文。
2. `SWEAgent` 创建内存时将该 ID 传给 memory manager；内存实例的 dialog 路径为 `dialog/<chat_id>`。
3. 压缩生成有效摘要后，按以下提交顺序完成：
   1. 将待压缩消息写入新建的 `<boundary_id>.jsonl`；
   2. 以原子替换写入 `manifest.json` 中的压缩边界；manifest 是唯一已提交来源；
   3. 从在线 memory 移除这批消息，并更新压缩摘要。
4. 任一归档或边界写入步骤失败时，不生成“已压缩”边界，也不得移除在线消息；UI 不报告成功压缩。进程在 manifest 提交前中断时，遗留批次文件不对 API 可见，可由后续维护任务清理。
5. manifest 提交后，当前活跃聊天通过专用非消息流事件接收该边界并立即渲染分割线；刷新后的详情和历史读取恢复同一边界。

自动压缩与显式 `/compact` 的成功路径不再写入“开始压缩”“压缩完成”或摘要正文等普通 assistant 消息；分割线是唯一的成功提示。压缩失败仍保留用户可见的错误提示，但不创建边界。

`/new` 与 `/clear` 不创建 **Conversation Compaction Boundary**，其历史不会从聊天时间线重新加载。

没有 `chat_id` 的非 Console 或直接 Agent 调用沿用既有 ReMe 归档行为，但不创建 **Conversation Compaction Boundary**，也不提供懒加载历史；不得伪造或共享一个聊天记录归档目录。

现有 ReMe 共享日期归档不再用于新的 UI 历史读取。没有会话目录与 manifest 的旧归档继续保留，但不在 UI 中猜测展示。

## 读取 API

现有 `GET /chats/{chat_id}` 保持兼容，并增加可选归档摘要信息：是否存在更早历史，以及紧邻在线消息的压缩边界。

新增：

```text
GET /chats/{chat_id}/history?before=<opaque-cursor>&limit=50
```

响应包含：

- 当前页更早的原始消息；
- 位于当前页时间范围内或恰好相邻的压缩边界；
- `has_more`；
- `next_cursor`。

游标是服务端生成的、不透明的定位符，保证相同时间戳下仍按消息 ID 稳定排序。读取严格限制在 `dialog/<chat_id>`，并验证聊天存在。
缺省页大小为 50 条展示安全消息。

## 前端体验

### 分割线

在每个压缩边界处插入非对话 UI 项：

```text
──────── 会话已压缩 · N 条消息已归档 ────────
```

分割线不展开摘要。它以 `last_message_id` 为锚点，始终位于该批归档消息之后、后续消息之前。首次进入聊天时，仅渲染与在线消息相邻的边界；加载更多历史后按页补充更早的边界。

### 向上懒加载

消息列表顶部使用观察哨兵；接近顶部时自动请求上一页。实现必须：

- 以单会话请求状态防止并发和重复请求；
- 对消息与边界按稳定 ID 去重；
- prepend 历史后依据滚动容器高度补偿 `scrollTop`，保证视口不跳动；
- 新消息到达时维持现有自动滚到底部行为；
- 加载中显示“正在加载更早的会话…”；
- 失败时保留现有列表并提供重试；
- 没有更多消息时显示“已到最早消息”。

## 兼容性和异常处理

- 没有归档目录或 manifest 的聊天沿用现有 UI 和 API 行为；
- 压缩摘要生成失败、归档写入失败或 manifest 更新失败，都不显示成功的压缩分割线；
- API 读取损坏的单行 JSONL 时跳过该行并记录错误，不使整个聊天详情失败；
- 不允许跨 `chat_id` 读取文件，避免路径穿越与会话数据泄露。
- 删除聊天记录时同步永久删除该聊天记录的 **Conversation Compaction Archive**，不改变现有 session state 删除策略。

## 验证

后端测试覆盖：

- chat ID 隔离及路径校验；
- 成功压缩的消息、manifest 与在线内存状态；
- 失败时不删除在线消息、不创建边界；
- 多压缩批次和相同时间戳的稳定分页；
- 多次压缩边界的排序和 API 返回。

前端测试覆盖：

- 初始边界渲染；
- 自动加载、去重与 `has_more`；
- prepend 后滚动位置保持；
- 加载失败重试和无更多历史状态；
- 新消息仍滚动到底部。

## 非目标

- 不在 UI 展开或展示压缩摘要；
- 不回填没有 chat ID 索引的旧日期归档；
- 不更改上下文阈值、压缩 prompt 或长期记忆策略。
