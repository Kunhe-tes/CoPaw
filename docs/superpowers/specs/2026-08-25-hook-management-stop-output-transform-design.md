# Hook 管理页 Stop 输出转换配置设计

**状态：** 已确认
**关联：** [Stop 输出转换运行时设计](2026-08-24-stop-output-transformation-design.md)

## 1. 目标与范围

让管理员能够在 Hook 管理页为 `Stop` 事件下的 `command`、`http` 和
`prompt` 处理器配置 `outputTransform`，并理解该配置对最终回复、失败策略
与处理器顺序的影响。

本次只补足管理页体验。继续使用既有 `GET/PUT
/hook-management/configuration` 配置接口和运行时校验；不改变 Hook 执行、
配置存储、Agent 重载或分发逻辑。

## 2. 现状与约束

`outputTransform: true` 已由运行时与 Hook 管理服务校验并持久化。它只允许
用于 `Stop`，且不能和 `once: true` 共存。三个处理器类型共用同一字段与返回
契约。

转换器按既有声明顺序串行运行，每个处理器接收当前文本；转换完成后，普通
Stop 校验器才会针对最终文本运行。候选文本必须在转换阶段结束后才可交付。

| 场景 | 运行时行为 |
| --- | --- |
| 处理器失败或输出无效，`failPolicy=allow` | 保留当前文本，继续其余转换器和最终校验 |
| 处理器失败或输出无效，`failPolicy=block` | 终止最终回复 |
| 全部转换器共享的时间预算耗尽（默认 30 秒） | 终止最终回复，独立于单处理器的 `failPolicy` |
| `replacementText` 缺失 | 当前文本原样传递 |

转换器只能返回 `decision: "allow"`，可选
`hookSpecificOutput.replacementText`。后者必须是非空字符串。`block` 不是转换
器的合法业务输出；阻断来自处理器失败时采用的 `failPolicy` 或普通 Stop
校验器。

## 3. 方案选择

采用“扩展既有处理器详情和编排视图”的方案：

- 不新增 Stop 专用双阶段编辑器，避免与现有统一分组、排序和分发模型分叉；
- 不新增能力元数据接口，避免为单一字段引入前后端配置同步问题；
- 通过 Stop 专属详情卡片、编排标签与人工测试提示表达转换语义。

## 4. 页面与交互

### 4.1 处理器详情

当编辑 `Stop` 的任意处理器时，在处理器详情中显示“转换最终回复”卡片；其他
事件不显示该卡片。

卡片包含：

- `Switch`：对应 `outputTransform`；
- 开启说明：候选回复会暂存，只有转换与最终校验通过后的文本会交付；
- 返回契约示例，使用固定只读 JSON：

```json
{
  "decision": "allow",
  "reason": "formatted response",
  "hookSpecificOutput": {
    "replacementText": "完整替换后的文本"
  }
}
```

- 约束提示：`replacementText` 可省略；不能使用 `block` 或其他副作用字段；
  三种处理器的配置方式相同。

开启开关时，前端立即写入 `outputTransform: true` 并将 `once` 设为 `false`。
“仅执行一次”开关在转换开启时禁用，并给出“不支持与输出转换同时使用”的原因。
关闭转换不自动恢复此前的 `once` 值，避免隐式改变管理员已确认的配置。

### 4.2 失败策略

保留既有“失败策略”选择器及其按处理器类型的默认值：`command` 和 `http` 为
`allow`，`prompt` 为 `block`。当 `outputTransform` 已开启时，在选择器下追加
上述运行时行为说明，特别标明总时间预算耗尽始终阻断，而不是把它表述为
`failPolicy` 的效果。

### 4.3 编排与排序

已开启转换的流水线条目显示“输出转换”标签。处理器仍在同一个分组和现有排序
控件中移动；该顺序就是转换文本的串行顺序。普通 Stop 校验器无需移动到另一
区域，它们继续由运行时在转换阶段之后执行。

### 4.4 人工测试

人工测试沿用单处理器真实执行。对于开启转换的处理器：

- 打开测试对话框时，预填 `assistant_response` 示例，并在提交前要求它是非空
  字符串；
- 结果展示 `output_transform`、`replacement_applied`、`replacement_length`、
  `failed` 与 `failure_type`；不回显候选或替换后的正文；
- 明确提示：测试不保存草稿、不重载 Agent，也不模拟多转换器串行链路、跨来源
  合并或总时间预算。

## 5. 数据与接口边界

前端草稿和请求体继续使用处理器对象中的 `outputTransform: boolean`。不创建
新路由、请求字段或服务端默认值。保存时由现有 Pydantic 模型作为唯一规则源：
前端防止明显错误，服务端仍拒绝非 Stop 或 `once: true` 的非法组合，并以 422
响应返回给页面。

既有保存后的 Agent 重载及“分发到 Default Agent”直接携带规范化的 Hook 分组，
因此输出转换配置随其原有事务和回滚语义分发，无需特殊分支。

## 6. 错误与可访问性

- 保存发生 422 时，保留草稿并在页面展示服务端校验信息；
- 409 冲突继续沿用当前刷新/重试语义，不静默覆盖其他管理员的配置；
- 所有开关保留可访问名称，禁用的 `once` 附带可读原因；
- 契约与失败策略说明使用文本，不能只依赖标签颜色。

## 7. 验收与验证

前端测试覆盖：

1. 三种处理器在 Stop 中均显示并能保存输出转换开关；非 Stop 不显示；
2. 开启转换会清除并禁用 `once`，关闭后不恢复其旧值；
3. 流水线条目带有输出转换标签，排序仍修改同一处理器序列；
4. 转换状态下人工测试要求 `assistant_response`，并仅展示脱敏摘要；
5. `failPolicy` 说明准确区分单处理器失败与全局预算耗尽；
6. 既有 Hook 管理页、保存、冲突、脚本上传和分发测试继续通过。

后端不新增业务分支；保留并运行现有 schema、手工测试、Stop finalization 和
runner 回归测试，以确保页面提交的配置与运行时契约一致。

## 8. 非目标

- 不增加全文回显、历史版本或原候选文本审计；
- 不在控制台模拟完整转换管道或提供逐处理器链路调试；
- 不改变 30 秒默认总时间预算、三类处理器的默认失败策略，或 Stop 校验器的
  后续行为；
- 不支持非文本内容转换。
