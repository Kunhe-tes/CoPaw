# 压缩历史分组与工具配对修复方案

状态：已实施（2026-10-28）。本文记录方案、实现边界与验证结果。

实现结果：历史 runtime 片段获得稳定的展示 ID，保留 `metadata.original_id`；
跨分页和压缩边界的同一响应会重新组装；工具输入/输出按显式调用 ID 双向配对；
阅读锚点会映射到合并后的卡片。在线 SSE 的原有 ID 与生产数据未改写。

## 问题与证据

生产已通过相同 call_id 确认：一次工具调用的输入与输出被显示为不同轮次；
部分工具卡只有输入或只有输出。问题发生在加载压缩 history，历史消息没有
turn_id/trace_id。不能要求这些旧数据先补出执行身份才能恢复正常展示。

本地已核实三处独立机制：

1. `convertArchivedPage()` 在压缩边界分段转换；每页转换后
   `MessageList.loadOlderHistory()` 仅前插，不重新组装跨页响应。
   相同一批消息可从 1 用户卡 + 1 响应卡变成 1 用户卡 + 3 响应卡。
2. `agentscope_msg_to_message()` 将单条 Msg 拆为 reasoning、tool use 等 runtime
   片段时，为多个片段设置同一个 id。`loadOlderHistory()` 的逐消息去重集合立即
   登记该 id，所以同页后续片段会被过滤。实测“思考 + 两次工具调用”产生 3 个
   同 id 片段，实际前端过滤逻辑只保留思考，丢掉两次调用。
3. `mergeToolMessages()` 只在遍历到输出时查找之前的输入。实际函数实测：
   输入→输出合为 1 项、content 长度 2；输出→输入保留 2 项、各只有单侧内容。

第 2 项属于前端接收后的展示数据损失，不代表磁盘归档缺失。第 3 项是独立的
顺序敏感缺陷，不代表生产一定发生了输出在前；需要回归保护这一条件。

## 方案比较

- 增大分页或预取到完整一轮：不能解决同 id 片段丢失；长工具链无自然页面上限，
  不作为修复方案。
- 只修片段 ID 与工具配对：改动较小，可以解决单侧工具卡的一部分原因，
  但用户仍会看到跨页拆开的响应块。
- 推荐：统一已加载历史的组装、片段身份与工具配对，一并解决三处问题。
  沿用现有分页、接口路由、压缩存储和滚动锚点机制。

## 推荐方案的行为

### 片段身份

原始 source message 身份与 runtime fragment 身份分开。
`metadata.original_id` 继续表示原始 Msg；同一原始 Msg 展开的多个 runtime 片段
使用不同且稳定的展示 ID。纯单片段消息尽量保留现有 ID。
前端不能仅按 original_id 丢弃片段；旧服务返回重复 id 时也要保留不同类型或
不同 call_id 的片段。实际完全重复的归档数据仍去重。

后端如果调整 runtime fragment ID，必须审查历史接口、Answer Turn 查询、
分享和在线 SSE 对原始身份的使用，确保它们继续通过 original_id 关联原始消息。
前端降级策略也不能以消息正文的偶然相同替代来源身份。

### 已加载历史组装

保留按存储顺序排列的原始消息和压缩边界信息。更早分页插入后，对连续的已加载
历史统一组装，不能把每次 HTTP 分页或压缩边界当成一次新的回答。
user 消息、明确的独立 Stop 附加输出及任务运行边界继续遵守已有独立展示语义。
不按时间重新排序，不推断未知的用户提交，不合成用户输入。

压缩提示继续保留在对应消息位置；若位于同一响应内部，以过程内的分隔信息呈现，
不通过新建另一张独立回答卡来表示。只对已经加载到的内容组装，未加载部分保持
现有历史加载入口，不无限预取。

旧数据没有执行身份时，只能恢复可证实的连续展示关系，不能宣称还原全部真实轮次。
至少保证相同 call_id 的调用及结果在已加载范围内正确配对；若存在明确用户边界，
不越过它将两次执行合并。确实缺失单侧数据时保留已有内容，不编造另一侧。

### 工具配对

在同一逻辑响应的已加载范围内按 call_id 建立双向配对，输入输出的数组先后顺序
不影响配对。不依赖工具名称配对同名并发调用，不修改原始消息对象。
保留输出侧终态、错误及治理状态；重复加载不重复添加输出，不覆盖其他调用。

### 滚动与生命周期

统一组装导致响应卡合并时，原有可见滚动锚点需要映射到保留的来源消息，避免
上翻加载后跳动。继续保留 session/generation 检查、请求锁、错误重试、
has_more/next_cursor 终止规则，旧会话请求不可写回新会话。

## 验证标准

先建立失败回归，再实现最小修复：

1. 一条 Msg 中 thinking + 多个 tool_use，以及多个 tool_result，history 全部保留。
2. 同 call_id 输入/输出跨分页、跨压缩边界，合并后仍能配对且只出现一次。
3. 工具输出先到、输入后到，已加载完整后合为一张工具卡。
4. 并发同名工具、不同 call_id 不串结果；单侧真正缺失时不合成内容。
5. 不同分页大小及先后加载方式，对同一已加载消息集合产生相同的逻辑响应分组。
6. 两个明确 user 回合、Stop 附加消息、任务运行边界不被错误合并。
7. 重复加载、切换会话、失败重试、压缩刷新不重复、不串会话。
8. 上翻加载与卡片合并后阅读锚点稳定；原输入和最终回答均可找到。

执行结果：相关前端测试 228 项通过，相关后端测试 51 项通过，typecheck、生产构建、
Prettier 和 `git diff --check` 通过。定向 ESLint 通过，新增 effect 依赖提示已修复；
完整变更范围仍有既有 `types.tsx` 的 `any` 错误。未做生产部署，也未通过真实生产会话验证。
本地浏览器跨页 QA 未执行，因为当前浏览器访问宿主不可用；MessageList 集成测试覆盖
了锚点恢复。旧历史没有 `turn_id`/`trace_id` 时只能合并可证实的连续内容，不能恢复
物理上已经不存在的用户原文或推断全部真实执行边界。
本方案不涉及生产数据改写或历史修复迁移。

## 检视修正：过程区子锚点

合并响应保存的 `historyAnchorIds` 是响应卡别名，而过程区 DOM 锚点使用
`process:<response-id>`。原解析器直接查找整个字符串，无法关联旧响应的子锚点，
导致归档加载后跳过滚动恢复。现在解析时保留 `process:` 前缀，通过响应 ID 别名
找到合并后的卡片，再返回它的过程区锚点。runtime 内容锚点及未知锚点保持原值。
新增回归覆盖多次合并的子锚点映射，以及实际 MessageList 归档加载后的滚动偏移。
修正后相关前端测试 230 项通过，TypeScript、定向 ESLint、Prettier 与差异检查通过。
