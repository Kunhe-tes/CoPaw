# 显式选择专家的后台执行可靠性设计（评审稿）

## 范围和目标

针对 Source 的专家主执行开关关闭时，显式选择专家后通过 `start_subagent` 启动并由 Main Agent 汇总的路径。开关开启时的专家主执行、普通 SubAgent 的公开 `wait_subagent` 契约、Plan/Goal 和专家选择 UI 均不改变。已合入的工具文本块解析修复继续保留。

成功标准：一次消息只跟踪其启动的运行；历史运行不能影响本次等待；等待不持续消耗 Main Agent 的推理迭代次数；异常和停止有确定的终止结果；Main Agent 仅在取得本次专家的可信终态结果后汇总，不能静默替换专家。

## 方案比较

1. **推荐：受保护的单次定向等待。** 启动成功后发起一次内部定向等待工具调用，内部异步检查指定 run，直到终态、失败、取消或截止时间。仍经过工具防护和 Hook，轮询不进入 ReAct 的多次迭代。需明确专用超时、取消和结果落盘。
2. **继续使用短等待工具调用。** 加 run_id 过滤、退避、错误上限，再调整 ReAct 的迭代计数。改动小，但须改变或绕过框架迭代循环，等待消息和 Hook 会重复，容易再次出现上限问题。
3. **转向持久化任务和异步事件通知。** 可以支持重启恢复和跨实例协调，但涉及会话续接、分布式所有权和消息协议，远超本次修复。

## 执行流程

1. 保留现有受保护的 `start_subagent` 调用、专家定义快照及所有权校验。只有确认 `accepted` 和非空 run_id 后进入等待。启动返回终态记录时，仍通过定向读取取得规范结果。
2. 强制执行内部专用的定向等待：参数只接受当前请求上下文中的 run_id，不能由模型或客户端替换；读取前及读取时沿用 tenant、Agent、session 和 chat 的访问边界。不得为了等待而调用无界的 `wait_for_run`，因为它依赖本进程句柄且没有超时。
3. 一次工具调用内以异步、有上界的间隔读取该 run 的持久记录并触发既有安全的 reap。其他运行的状态不决定返回时机；不扫描全会话历史。内部等待不能占用事件循环，也不新增每次轮询的会话消息。
4. 返回状态为 `completed`、`partial`、`failed`、`cancelled`、`expired` 时携带现有 parent-facing 投影。只有获取到目标 run 的合法终态，才结束等待并交给 Main Agent 根据实际状态和结果汇总；失败、取消和过期不得表述为成功。
5. `not_found` 不代表专家已完成。首次不存在可短暂重读以覆盖存储可见性延迟；连续不可见达到小的固定重试预算后停止并报告“运行状态不可确认”，不让 Main Agent 补做任务。存储错误与记录不存在分别记录类别，公开信息不包含路径、密钥或原始异常。无效结果、未知状态同样有限重试并最终明确失败。

## 超时、取消与所有权

- 等待截止时间由本次已冻结的有效专家执行预算 `timeout_ms` 加有限的收尾余量确定；包括启动到终态的总耗时，而不是每次重试重置。沿用更严格的外层请求/部署截止时间。实现时应固定并测试收尾余量，不能无限等待。
- 内部定向等待需要独立的专用超时管理，避免被普通本地工具硬超时提前截断；该例外仅适用于服务端生成、绑定当前 run 的内部调用，不能对模型可控工具或普通 `wait_subagent` 全局放宽。仍执行现有工具防护、审批与 Pre/Post Tool Use Hook；Hook 拒绝、要求审批或终止时按既有流程退出，不绕过防护。
- 用户停止、请求取消或等待达到截止时间时，尝试通过现有 supervisor 对该 run 做幂等取消，并等待有界清理。取消返回不可管理、记录缺失或清理超时时，只报告“取消未确认/状态不可确认”，不能声称进程已停止。取消与自然完成竞争时，以持久化的真实终态为准；若无法读取，则报告未确认。
- 必须覆盖启动成功与 run_id 写入上下文之间的取消竞态：从启动成功的结果中在可能取消前登记 run_id，或由启动流程在取消时按当前 turn 的真实所有权清理；不得依靠仅在下一次 reasoning 才记录 run_id。不得用跨进程 PID 假设取消其他实例任务。
- 等待超时或状态不可确认时不自动重新启动，也不交由 Main Agent 替代执行；避免重复业务操作。专家可能仍在后台运行的情况应明确告知，按现有监控入口查看。

## 错误和可观测性

启动拒绝区分并发限制、专家不可用、请求无效及其他失败；内部异常分类记录在服务端，界面使用安全、可操作的文案。报告所选专家未被替代。日志仅包含租户/会话/运行关联标识、阶段、状态及错误类别，遵循现有脱敏策略，不输出任务正文、工具参数或私有依赖。保留现有工具结果及事件结构，避免泄露内部路径。

## 验收测试

- 使用真实 `ToolResponse` 文本块和实际消息内存，覆盖启动成功、终态读取、失败与拒绝，不以字符串模拟代替实际封装。
- 同一 chat 先有历史终态，再启动慢运行：历史记录不使目标等待提前结束；目标终态恰好返回一次。并发其他运行、不同 chat/租户和跨实例不可管理场景均不泄漏或误归属。
- 以小 `max_iters` 运行真实 ReAct 循环：长于多个原 3 秒周期的专家运行仍能等到终态；不得提前汇总，且等待不会无限增加会话消息或迭代。覆盖运行在最后允许迭代结束时的边界。
- 持久记录暂时不可见后恢复、持续不可见、读取异常、未知状态、真实失败以及运行超时均在预算内结束并报告正确结果；无自动重启与主 Agent 替代。
- 启动期间和等待期间停止、自然完成与取消竞争、取消失败、不可管理和清理超时，检查仅操作目标 run，且状态表述与持久结果一致。
- 审批、拒绝、Hook 和工具硬超时边界保持有效；一般 `wait_subagent`、新版专家主执行与已有子 Agent 管理测试不回归。用可控时钟和事件驱动测试，而不是依赖真实长时间 sleep。

## 实施前需进一步确认

审查现有运行记录的创建时间、有效预算传递与外层截止时间，确定可计算且重试不重置的绝对截止时间；确定现有 Hook 和审批对内部专用调用的注册方式，以及跨 Pod 不可管理时的用户提示。若当前运行身份或预算无法在启动结果中可靠获取，先扩展服务端内部契约并测试，不从模型文本推断。

## 实施结果

方案已落地：选中专家使用服务端绑定的单次定向等待，启动运行 ID 在服务端上下文登记；等待和取消均受总预算约束，无法确认时明确返回不确定状态。审批恢复携带并校验租户、Agent、会话、聊天和专家身份元数据，只恢复原运行等待，不重新启动专家。普通 `wait_subagent` 契约保持不变。
