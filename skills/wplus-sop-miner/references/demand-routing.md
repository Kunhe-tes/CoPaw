# 需求路由与环节队列

## 先判断承载方式

1. 若已有技能能够完整处理当前领域和交付物，使用已有技能。
2. 若没有合适技能，但用户正在澄清一个具体、可重复的工作流程，使用本技能的通用兜底模式。
3. 若需求涉及 W+ 页面、客户名单、资产、产品、收益或跟进，使用 W+ 模式。

通用兜底模式仍执行逐环节澄清和预跑，但不引用 W+ 页面、记忆或 OpenCLI 能力。

## 优先识别名单分析流程

如果需求同时包含以下语义，就优先提议固定主流程：

- 从较大范围形成候选客户名单；
- 使用更细条件筛出目标客户；
- 对筛选结果做原因、价值、风险、优先级或行动建议分析。

推荐队列：

```text
初筛客户列表 → 精筛客户 → 分析结果
```

- 保留这三个主环节的语义，不因页面或字段差异随意改名。
- 若用户还要求触达、建任务或跟进记录，可提议第 4 个环节“执行跟进动作”。
- 若需求明显不具备“初筛—精筛—分析”结构，按实际动作设计 2–4 个环节，不强套模板。

## 队列设计原则

- 每个环节对应一段可独立澄清和预跑的真实操作。
- 使用动宾结构或短动作链，不使用“目标、页面、数据、分析、输出”等内部检查维度作为环节名。
- 最多 4 个主环节；复杂细节作为环节内步骤处理。
- 平台功能图中的路径只作为候选，必须由用户确认实际顺序。

## 第一次回应

普通 Chat 中，第一次回应只能用 Markdown 展示队列，不得同时提出第一个
环节问题：

```markdown
## 需求拆解

1. {环节 1}
2. {环节 2}
3. {环节 3}

这个顺序是否符合你的实际工作？确认后我会从【{环节 1}】开始，并在每个环节澄清完成后立即预跑、吸收反馈，再进入下一环节。
```

用户调整队列后重新展示最终队列并等待确认。确认后把第一环节设为 `clarifying`，再按 `question-policy.md` 提问。

CoPaw 工作台不是上述 Markdown 展示路径。平台已提供
`wplus_sop_session_id` 与 `emit_wplus_sop_event` 时，第一次回应必须且只能
调用一次 `emit_wplus_sop_event(kind='stage_proposal', ...)`；不得只输出
Markdown。事件 `payload` 的最小契约为：

```json
{
  "stages": [
    {
      "stage_id": "stage-1",
      "name": "确认需求范围",
      "description": "确认流程入口、对象范围与目标。",
      "status": "pending"
    },
    {
      "stage_id": "stage-2",
      "name": "验证交付结果",
      "description": "预跑已确认流程并核对输出。",
      "status": "pending"
    }
  ]
}
```

`references/state-schema.json` 的 `stage_queue[].id` 属于 Miner 内部业务状态；
构造工作台 `stage_proposal` 事件时，把它映射为 `stages[].stage_id`。事件中
不得使用含义不明确的 `id` 代替 `stage_id`。结构化事件提交成功后可以附加
Markdown 摘要，但该摘要不承载工作台状态。
