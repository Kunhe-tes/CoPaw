# 澄清问题策略

## 建立问题清单

进入一个环节时，先在内部建立当前问题清单，覆盖该环节适用的入口、输入、范围、口径、规则、输出和下一动作。用 `question_total` 记录当前总项数，用 `question_resolved` 记录已确认、明确未知或不适用的项。

- 反馈暴露新缺口时可以增加 `question_total`。
- 不重复询问已经解决的问题。
- 每轮只选能消除最大流程分支的 1–3 个问题。
- 不输出内部推理、证据标签、长篇背景或其他环节的未确认内容。

## 固定输出格式

```markdown
## 【环节 {current}/{total}：{环节名}】澄清

进度：已澄清 {resolved}/{question_total} 个问题｜本轮 {count} 题

### 1. {问题标题}
{仅在必要时用一句话说明答案会影响什么。}

A. {选项}

B. {选项}

其他：{请补充}

### 2. {问题标题}
...

回复示例：`1A，2B`；也可以直接补充实际做法。
```

只在 W+ 已知路径有助于定位时，在标题后增加一行：

```markdown
> 已知路径线索：{页面路径}（仅作定位，仍以你的实际操作为准）
```

不得在澄清问题中展示具体 CLI 命令；OpenCLI 只在当前环节预跑提示中出现。

## 后续轮次

同一环节第二轮及以后，只用一行总结当前环节已确认内容和剩余缺口：

```markdown
**当前已确认：{简短事实}；还需确认：{剩余缺口}。**
```

随后立即使用固定问题格式。不要复述完整对话，不要总结其他环节。

## 问题优先级

通常按以下顺序消除缺口：

1. 实际动作、触发条件和环节输入；
2. 页面或人工入口；
3. 客群、产品、时间等范围；
4. 字段、指标和对比基线；
5. 判断阈值与分支；
6. 环节输出和下一动作；
7. 相关时再问频率、批量规模、排序和触达限制。

只有选项来源明确时才提供选项；否则提出一个简短开放问题。不得询问 MCP，也不得询问是否生成新技能。

## 证据边界

拟定选项不是用户事实时，在内部标记为 `page_evidence`、`capability_registry` 或 `memory_hypothesis`。记忆假设必须用待确认语气；任何冲突都以用户本轮说法为准。
